# 技术与验收说明

## 本地架构

- React + TypeScript前端，FastAPI后端，SQLite数据库。
- 金额以HKD分保存；费率以basis points保存；API拒绝任何会在转换为分或bps时静默改值的超精度输入。
- Tesseract在本机处理JPG、PNG及无文字层PDF；长截图分块识别，有原生文字层的PDF优先读取全部页面文字。用户主动启用AI时，Codex App Server通过应用专用ChatGPT管理登录调用固定 `gpt-5.6-luna` 进行一次图像识别。
- 原文件、解析器版本、本地OCR结果、AI结果、冲突、人工修订及哈希分别归档。AI不得覆盖本地OCR原值。
- Alembic管理数据库结构；Settlement冻结Company/FC，SettlementAccountLine冻结账户级前序HWM来源。QuarterlySettlement以自然键加`version_no`永久唯一、`status != 'VOID'`活动唯一，并用`replaces_settlement_id`保留不可覆盖的替代链。Invoice以Client+年度+季度+Fee Plan为活动唯一组，InvoiceSource/InvoiceLine冻结跨Platform来源及逐账户收费，InvoiceIssueAttempt记录编号预留和恢复；Payment、PaymentAllocation、PaymentRefund、InvoiceAdjustment及InvoiceCorrection构成追加式现金/更正台账。SQLite Trigger兜底同账户同季度不重复、Finalized期间流水/Snapshot/证据关系、结算顺序、核心整数公式、收益率、Settlement版本、Invoice来源全集、二态付款凭证、每轮REVERSAL和全链现金守恒及台账不可变；应用只绑定127.0.0.1。
- 四类基础设置删除采用“应用层完整引用检查 + SQL DELETE + SQLite RESTRICT外键”双层保护，禁止ORM关系同步把Client等可空外键改为NULL。AuditEvent、Attachment和ExportRecord的旧式`entity_type`先统一大小写、首尾空格及空格/连字符后再检查；成功删除与最小识别字段写入AuditEvent，不复制或删除任何客户文件。

## ChatGPT Pro辅助识别边界

- 连接只使用本机 Codex App Server 的 `stdio`；不要求或保存 OpenAI API Key。
- 使用应用专用、干净的 `CODEX_HOME`；不得复用或复制桌面Codex凭据，不得加载全局/项目AGENTS、插件、Hook或MCP。退出Luna登录不得影响桌面Codex。
- 启动识别前读取账号、订阅类型、使用额度及模型列表；只有ChatGPT已登录且精确模型ID `gpt-5.6-luna` 可用时才发送图片。
- 模型ID固定，不接受前端传入模型，不采纳模型目录中的 `upgrade` 建议，不静默路由到其他模型，也不进行第二次模型识别。
- AI结果必须满足结构化字段约束；响应声称使用其他模型、协议异常、超时、未登录、额度不足或模型不可用时统一降级为人工复核。
- OCR与AI按标准化后的字段逐一比较。任何冲突都保留双方原值并设置人工复核标记；不存在“AI自动胜出”规则。
- AI识别只更新Statement Import的辅助识别及审计字段，不能创建或修改Balance Snapshot、Transaction、Settlement、Invoice或Payment。
- 本地OCR与Luna均须分类文档类型；供款记录、资产转入记录及未知文件在服务端硬性禁止生成Balance Snapshot。
- 正式确认仍调用独立确认接口，并继续执行关键字段、重复文件、账户匹配及日期资格校验。

官方依据：[Codex App Server](https://learn.chatgpt.com/docs/app-server) 支持ChatGPT管理登录、账户额度、模型列表、图片输入和本地 `stdio`；[GPT-5.6 Luna模型页](https://developers.openai.com/api/docs/models/gpt-5.6-luna)确认其模型ID、图片输入及结构化输出能力。模型和订阅可用性以运行时检查为准。

## 账单确认、余额与Settlement数据链

- `POST /api/statement-imports/{id}/confirm`是唯一正式入账入口。它在同一数据库事务中保存人工确认值和持仓，建立`source_type=STATEMENT_IMPORT`且带`statement_import_id`的BalanceSnapshot，把`confirmed_account_id`、`confirmed_snapshot_id`写回StatementImport，并记录`STATEMENT_CONFIRMED` AuditEvent。
- 原始Statement Import文件通过`statement_import_id`构成Snapshot来源证据；StatementImport保留本地OCR、Luna候选、人工值及修订轨迹。确认结果页和资金页据此显示原账单、账户及Snapshot关系，不复制或重写原始文件。
- 相同Account Number可存在于不同Platform。确认时若账号只匹配一个Sub Account可自动采用；多条候选只有在Scheme唯一匹配时可自动采用，否则返回409并要求明确选择。所有账户选择项使用Client、Platform、Account Number和Scheme共同标识；复核页切换导入记录会清空旧选择，显式选择时请求同时携带并由后端核对`account_platform_id`。
- `GET /api/transactions`只读扩展返回Client、Platform、Fee Plan和Scheme身份字段；`GET /api/balance-snapshots`除同组身份外还返回`statement_import_id`与`holdings`。Settlement账户行和Invoice账户行的只读响应也返回`scheme_name`，其中Invoice的Scheme明确标为当前Sub Account主资料参考，Fee Plan及已冻结Platform/Account Number/期间/Service Fee仍是正式账单依据。该组只读字段是0.2.12行为；0.2.14另有Settlement版本和付款台账Alembic迁移，但不改变Scheme仍是当前资料参考的口径。
- BalanceSnapshot只表示一个Sub Account在一个日期的余额。确认余额页不会创建TransactionRecord；供款记录、资产转入记录和累计净供款也不会自动映射为Contribution/Withdrawal。资金流水必须由财务单独选择账户、日期、类型和金额后登记并关联凭证。
- 导入Snapshot只有在日期为季末或等于该账户实际`end_date`时才自动获得Closing资格；其他日期只作普通快照。若确认时建立DRAFT Client/Sub Account，须补齐Company、FC、Platform、Fee Plan、开始管理日期及适用的实际结束日期并激活；ACTIVE写入及季度结算均拒绝缺少`start_date`的遗留账户。账户`end_date`变化时，若新日期早于该账户任何未作废Settlement的Closing Date立即409拒绝；通过后再重算未被Settlement引用的导入Snapshot资格。手工Snapshot保留人工False选择，只会在原True不再符合规则时降级；若资格变化会触及已引用Snapshot同样409拒绝，并记录审计。
- Statement确认不会自动建立、Calculate或Finalize QuarterlySettlement。结算页通过Balance Snapshot只读列表提供候选；财务逐账户选择期间、Beginning/Closing Snapshot及首次Original HWM后调用Calculate保存Draft。Finalize的第一条数据库语句取得SQLite `BEGIN IMMEDIATE`写锁，再由共享计算服务从当前数据库重查账户状态、冻结归属、费率、Snapshot、Transaction、前序HWM及同账户同季度冲突，并逐字段比对已存Draft；差异返回409，不静默改写旧Draft。内部Excel候选和历史Settlement列表从`account_lines`及账户只读资料逐行显示Sub Account号码与Scheme。Calculate与Finalize均要求Client及所有Sub Account仍为ACTIVE且账户具有开始管理日期，防止未确认、资料不完整或已关闭账户被正式锁定。历史表及结果同时显示`version_no`、直接替代来源和VOID原因；最新版本VOID后Calculate只建立下一连续版本，不原地复用。
- 凭证关联目标是受控状态；切换Snapshot/Transaction类型或Client、Platform、Sub Account筛选即清空旧ID。前端不得把一个实体类型下的旧数字ID与另一类型组合提交，避免错误满足Finalize凭证门槛。Finalize会对每个StatementImport/Attachment检查受控数据根、普通文件、非空、登记大小（如适用）及SHA-256；SQLite Trigger同时禁止在相关Settlement仍为Finalized时删除或改写证据关系，Void后才开放底层纠正。

## 计算公式

- Net Contribution = Contribution - Withdrawal
- Gain/Loss = Closing - Beginning - Net Contribution
- Period Rate = Gain/Loss / (Beginning + Net Contribution)
- Adjusted HWM = Original HWM + Net Contribution
- Watermark Difference = Closing - Adjusted HWM
- Service Fee = MAX(Watermark Difference, 0) × Fee Rate
- Next HWM = MAX(Adjusted HWM, Closing)

Days只展示，不参与收费。结算流水口径是`transaction_date > start_date AND transaction_date <= closing_date`；起始日资金应已包含在人工确认的Beginning Snapshot中，不再次计入Net Contribution，但数据库冻结口径故意使用`>= start_date`，因此起始日流水在Finalize后同样不可增删改。Finalize时逐Sub Account重新核对前序SettlementAccountLine/Next HWM，并保存固定公式版本、费率、账户构成、Company/FC归属及结果快照。HWM链只能按时间向后锁定、按时间倒序作废。

SQLite Trigger为避免精确PPM校验中的64位整数运算溢出，要求Beginning、Net Contribution和Gain/Loss三项各自的绝对值均不超过`9,000,000,000,000` cents（HKD 90,000,000,000）；任一项超过即停止迁移或Finalize并要求专门的高精度迁移。这是SQLite整数实现上限，不是收费业务上限，也不得被前端解释为客户额度。

Draft仅可通过`DELETE /api/settlements/{id}`删除，账户行由同一事务级联清理并写`SETTLEMENT_DRAFT_DELETED`审计；Finalized及Void明确拒绝。Finalized可从季度结算页面受控Void，但仍须先处理活动Invoice来源并按账户HWM依赖倒序操作。VOID历史继续保留原版本及明细；同自然键只对非VOID记录实施活动唯一，下一次Calculate建立`version_no + 1`并以唯一`replaces_settlement_id`指向最新VOID。应用及Trigger共同拒绝跨自然键替代、非连续版本、替代非VOID记录、同一旧版本被多次直接替代或并发建立两个活动版本。

## 备份与恢复不变量

- 创建备份使用SQLite Backup API，并在写ZIP前验证副本的`integrity_check`、`foreign_key_check`、金融系统核心表/列及已知Alembic版本；数据库目录、数据库文件及业务文件树中的symlink/junction一律拒绝。ZIP先写入同一备份目录的唯一临时名，按完整恢复规则自校验后以不覆盖的同目录原子`rename`公布；同秒或并发请求各自得到不同成品路径。
- 恢复要求唯一键JSON、受控相对路径、ZIP普通成员、Manifest精确字段、归档文件全集、逐文件SHA-256、唯一数据库及相同数据库身份；无关或未来迁移版本的SQLite即使结构自洽也拒绝。0.2.14还把数据库中的Payment/PaymentRefund凭证关系与归档`attachments/**`逐笔交叉核验：Attachment归属、唯一受控路径、非链接非空普通文件、数据库大小/SHA-256、Manifest SHA-256和归档实体内容必须完全一致；旧9d Payment缺证或删除凭证及其Manifest记录均不能通过。
- HTTP中间件以恢复专用读写门闩跟踪API财务写请求：普通写入保持既有并发能力并增加活动计数，恢复只在活动计数为0时独占进入，进入后新的写入直接409；恢复上传再从读取前使用专用非阻塞进程锁，第二恢复请求同样409。这样既不破坏Invoice/PDF既有并发契约，也保证恢复开始后不存在已越过marker检查仍在执行的并发写入。已验证pending树保持为不可变源；marker写入后中间件拒绝除安全退出外的全部API写入，恢复响应完成后由ShutdownCoordinator自动优雅停机，防止排队后新增数据在重启时被旧备份覆盖。系统下次启动在数据根同一卷的`tmp`中预制`database/attachments/statement_imports/output`四个完整目录并再次验证，再通过持久化journal和同盘目录`replace`切换；普通异常逆序回滚，进程中断由下次启动依据`preparing/applying/rolling_back/committed`恢复，完成前不会启动数据库服务。
- `committed`是不可逆点；marker、pending和旧目录清理由幂等收尾完成，失败只明确告警并保留journal供后续启动重试，不得把已成功恢复报成失败或回滚成混合代际。后续新恢复marker不会被旧committed事务误删。无引用旧pending及上传ZIP会在启动时按安全前缀重试清理。

## Invoice聚合与恢复不变量

- Draft由服务端按Client、年度、季度和Fee Plan查询全部Finalized Settlement，不接受前端提供金额或可选择来源；总额以各冻结账户行的整数分相加。候选、已选组合和Invoice明细必须显示Fee Plan，账户行同时显示`Scheme（当前资料）`供人工辨认具体Sub Account。
- 零收费Settlement仍进入来源和明细；只有整组总额大于0才生成Invoice。组内冻结Company/FC必须一致，不一致即拒绝合并。
- 同一客户季度计划最多一张Draft/Issuing/Issued Invoice，同一Settlement最多一个active InvoiceSource；Invoice Void由数据库触发器把全部来源置为inactive。OPEN Invoice Correction会阻止同组从旧Settlement直接重开，替代Invoice只能在原Settlement逐一形成完整`replaces`版本链后建立。
- Issue前应用及数据库触发器都重新确认同组Finalized来源全集、来源金额、逐行金额和Invoice总额一致。Draft建立后新增的迟到Settlement会阻止签发，必须作废重建。
- SQLite只允许`DRAFT→ISSUING/VOID`、`ISSUING→ISSUED/DRAFT`和`ISSUED→VOID`；离开Draft后金额、分组、Company/FC、Fee Plan和兼容Anchor不可修改，编号及Issue/Due Date只能在预留时写入或ISSUING退回Draft时清空。Source/Line不能跨Invoice改挂。
- Invoice PDF只使用Invoice冻结的Company/FC关系及InvoiceLine平台、账户、期间、Service Fee，不从Client当前Company/FC重新推导，也不把跨Platform合并扩散到HWM计算。当前Scheme只作界面识别参考，并未冻结进InvoiceLine；若未来要求历史账单永久保留Scheme名称，必须另做Schema迁移和冻结规则。
- Invoice编号为`Company全名-中介人名字缩写-IssueDateYYYYMMDD-N`。Company Code不参与编号；`N`按Company+FC持续递增且不按日期或格式切换重置，历史编号不改写。
- 预留编号时同时检查Invoice和InvoiceIssueAttempt历史号码。若Company全名候选与旧格式正式号或失败预留号碰撞，增加序号并写`INVOICE_NUMBER_COLLISION_SKIPPED`；唯一索引仍作为最终并发兜底，跳过号码不得复用。
- 编号预留、PDF渲染和最终提交分阶段执行。ISSUING恢复只有双语最终文件均在安全归档目录时才能COMPLETE；RETURN_TO_DRAFT删除部分文件但不回收编号，两者均更新InvoiceIssueAttempt和AuditEvent。
- 业务编号不得直接作为不受约束的Windows路径。0.2.12新签发及旧Issued缺档补建统一以完整业务号的SHA-256生成内部文件名，避免Windows大小写不敏感碰撞；旧版已登记路径直接沿用，遗留ISSUING的短ASCII原名仅作为兼容恢复候选。哈希/原名两套文件同时完整时拒绝自动完成，RETURN_TO_DRAFT清理两套路由及临时文件。下载名另做非法字符替换、长度上限和记录ID唯一化，PDF正文及数据库编号不变。
- Invoice所有动态业务字段使用可覆盖中文的Unicode字体；即使选择English PDF，中文Company全名和完整Invoice编号也必须可读取。
- 已登记Issued/VOID PDF下载前必须按Invoice、语言和存储路径匹配`PDF_INVOICE` ExportRecord并重算SHA-256；缺记录或哈希不符时拒绝返回并要求从备份恢复，不能重生成覆盖。
- `c4b7f1d92e60`迁移保留旧Invoice/Payment/归档字段；ACCOUNT_HWM逐账户回填，LEGACY_GROUP_HWM单行回填。金额不对平、重复活动组/来源或残缺新表时安全停止，不猜测修复。
- `7f3c2a91b6e4`从精确`9d2f6a8c4b13`及完整35-Trigger旧结构升级，在显式SQLite事务内重建Settlement版本表和Payment约束、新增四张账本表并回填旧Payment的初始APPLY。存量Settlement全部为v1且无替代来源。旧Payment只有在每张Invoice已被其Payment合计精确结清、每笔都一一关联非空且元数据完整的`PAYMENT`凭证、凭证不共用、无外键违规及无半迁移表时才可升级；任一条件不满足都在DDL前安全停止，不伪造凭证、不猜测尚未结清付款去向。历史上多笔Payment若合计恰好全额且凭证逐笔合规，则逐笔无损保留为初始APPLY；日常新Payment仍只允许唯一一次确认。迁移完成后核对原行数、外键、`integrity_check`、活动/版本索引及完整Trigger契约；downgrade拒绝，须从升级前完整备份恢复。
- 日常Payment只允许向Issued、没有任何Payment/Allocation/Adjustment的Invoice登记一次正数实际现金。请求必须引用未被占用的`PAYMENT`凭证，并在写入前验证受控路径、普通非空文件、大小和SHA-256；“未被占用”以Attachment关系及凭证外键为准，SHA-256只证明文件完整性，相同哈希不自动代表同一业务凭证。付款方式必须去空格后非空，应用Schema和SQLite Insert Trigger双层拒绝空白方式。Payment行冻结`company_difference_cents/difference_reason`，AFTER INSERT在同一SQLite语句内原子认领凭证、按需生成唯一Payment绑定的InvoiceAdjustment并建立等额初始APPLY。普通差额不能独立插入，任一子步骤失败会回滚整个Payment。`现金 + COMPANY_BORNE_DIFFERENCE = Invoice金额`必须精确成立，差额大于0必须有原因且差额为0时不得填写差额原因，故成功确认后付款状态直接从UNPAID进入PAID，不存在部分付款或第二笔付款。Due Date逾期是独立`is_overdue`标记。
- Payment表示原始现金事实，`invoice_id`不随更正改变。当前现金归属只由PaymentAllocation的APPLY/REVERSAL追加台账计算：REVERSAL必须等额引用且只能引用一次既有APPLY；普通InvoiceAdjustment必须以唯一`payment_id`绑定Payment且不得带Correction，更正差额则必须绑定Correction且不得带Payment。Payment、分配、退款和差额禁止更新/删除，付款及退款附件认领后也禁止改写或删除。Correction只允许从OPEN受控写入唯一替代Invoice并转为COMPLETED；业务字段任意改写、完成后再次改变及删除均禁止。
- Invoice Correction状态为`OPEN/COMPLETED`。OPEN原因及退款原因均须去空格后至少2字符，付款/退款方式须去空格后非空；中间flush约束失败统一回滚并返回409。OPEN在`BEGIN IMMEDIATE`内把Issued原Invoice转VOID并逐笔REVERSAL其当前活动APPLY；转VOID必须同时写2至500字符原因和作废时间，VOID后两字段由Trigger冻结。有现金时原Invoice必须已完整平账，无现金时可建立空更正。COMPLETED要求替代Invoice同Client/年度/季度/Fee Plan、为Issued且资金账本为空，其活动Settlement来源一一沿完整替代链回到原来源。符合该替代链的Issued候选在OPEN完成前必须保持资金空白，Payment接口及再次发起Correction都须拒绝；REVERSAL在OPEN立即生效，correction-linked APPLY、Refund和Adjustment只有状态成功切换到COMPLETED后才计入会计值，因此跨事务pending行不能提前把替代Invoice变为PAID。连续更正只能先完成上一轮，再由上一轮的当前Issued替代Invoice开启。每笔Payment的本轮保留APPLY加本轮退款必须等于本轮REVERSAL，全部保留现金加公司差额必须等于替代Invoice金额；退款必须有唯一`PAYMENT_REFUND`实体凭证。无REVERSAL完成则强制本轮无APPLY、退款及差额且替代单保持UNPAID。跨连续更正，数据库继续校验Payment净分配与累计退款不超过且最终守恒于最初现金，已经退款的金额不能再次分配。
