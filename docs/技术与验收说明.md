> 当前源码与正式Windows运行版均为0.2.19。0.2.19新增季度期初边界迁移，使自然季度可用上一季末Snapshot作为Beginning，并统一Calculate、Finalize、凭证保护和数据库Trigger的资金区间。

0.2.19已通过完整测试、Windows候选、正式备份、F盘隔离副本预检、同版本数据包恢复和正式运行版验收；精确结果记录在本文末尾。

## 本地架构

- React + TypeScript前端，FastAPI后端，SQLite数据库。
- 金额以HKD分保存；费率以basis points保存；API拒绝任何会在转换为分或bps时静默改值的超精度输入。
- Tesseract在本机处理JPG、PNG及无文字层PDF；长截图分块识别，有原生文字层的PDF优先读取全部页面文字。用户主动启用AI时，Codex App Server通过应用专用ChatGPT管理登录调用固定 `gpt-5.6-sol` 进行一次图像识别。
- 原文件、解析器版本、本地OCR结果、AI结果、冲突、人工修订及哈希分别归档。AI不得覆盖本地OCR原值。
- Alembic管理数据库结构；Settlement冻结Company/FC，SettlementAccountLine冻结账户级前序HWM来源。QuarterlySettlement以自然键加`version_no`永久唯一、`status != 'VOID'`活动唯一，并用`replaces_settlement_id`保留不可覆盖的替代链。Invoice以Client+年度+季度+Fee Plan为活动唯一组，InvoiceSource/InvoiceLine冻结跨Platform来源及逐账户收费，InvoiceIssueAttempt记录编号预留和恢复；Payment、PaymentAllocation、PaymentRefund、InvoiceAdjustment及InvoiceCorrection构成追加式现金/更正台账。SQLite Trigger兜底同账户同季度不重复、Finalized期间流水/Snapshot/证据关系、结算顺序、核心整数公式、收益率、Settlement版本、Invoice来源全集、二态付款凭证、每轮REVERSAL和全链现金守恒及台账不可变；0.2.15再增加四个Client/Account/Statement/Snapshot删除防护，总数57。应用只绑定127.0.0.1。
- Company、FC、Platform、Fee Plan、Client和Sub Account受控删除采用“应用层完整引用检查 + Core SQL DELETE + SQLite RESTRICT/Trigger”保护，禁止ORM关系同步把可空外键改为NULL。AuditEvent、Attachment和ExportRecord的旧式`entity_type`先统一大小写、首尾空格及空格/连字符后再检查；成功删除以`entity_id=NULL`和最小识别字段写入AuditEvent。Client/Sub Account删除不触碰任何客户文件，系统也不判断记录是不是测试数据。
- Client、Sub Account、Statement Import和Balance Snapshot的新建ID由`app_settings`四项持久高水位显式分配；迁移按现存最大ID和可验证删除审计播种，手工Snapshot及账单确认Snapshot均使用同一分配器。删除后的ID不再复用，防止旧AuditEvent中的原ID以后指向新记录。对升级前已发生的Statement ID复用，只有旧审计为唯一`STATEMENT_IMPORT_DELETED`、实体类型规范化后为`STATEMENT_IMPORT`、未含新版保留字段，且SQLite `julianday`能严格证明删除审计早于当前账单建立时间时，才能由`c1a7d5e9b402`消歧。迁移保留原details，写入`deleted_import_id`、三个版本/纠正标记并清空旧`entity_id`，再追加一条`LEGACY_STATEMENT_DELETE_ID_REUSE_DISAMBIGUATED`更正审计。运行时和备份会交叉验证两条审计的revision、证明、双向ID和时间字段；任一证据缺失或不唯一仍失败即停。同ID当前记录一旦后续按正常流程删除，新删除审计会恢复该ID的严格禁止复用语义。

## ChatGPT Pro辅助识别边界

- 连接只使用本机 Codex App Server 的 `stdio`；不要求或保存 OpenAI API Key。
- 使用应用专用、干净的 `CODEX_HOME`；不得复用或复制桌面Codex凭据，不得加载全局/项目AGENTS、插件、Hook或MCP。退出Sol登录不得影响桌面Codex。专用目录仍沿用历史名`LunaCodexHome`，只为保留现有登录，不代表调用Luna。
- 启动识别前读取账号、订阅类型、使用额度及模型列表；只有ChatGPT已登录且精确模型ID `gpt-5.6-sol` 可用时才发送图片。
- 模型ID固定，不接受前端传入模型，不采纳模型目录中的 `upgrade` 建议，不静默路由到其他模型，也不进行第二次模型识别。
- AI结果必须满足结构化字段约束；响应声称使用其他模型、协议异常、超时、未登录、额度不足或模型不可用时统一降级为人工复核。
- OCR与AI按标准化后的字段逐一比较。任何冲突都保留双方原值并设置人工复核标记；不存在“AI自动胜出”规则。
- AI识别只更新Statement Import的辅助识别及审计字段，不能创建或修改Balance Snapshot、Transaction、Settlement、Invoice或Payment。
- 本地OCR与Sol均须分类文档类型；供款记录、资产转入记录及未知文件在服务端硬性禁止生成Balance Snapshot。
- 正式确认仍调用独立确认接口，并继续执行关键字段、重复文件、账户匹配及日期资格校验。
- 上传/OCR、reparse、Sol、confirm和delete共享同一进程锁；异步上传在线程worker内覆盖文件保存、重复检查、OCR和数据库提交的完整临界区。原件在OCR前及OCR完成、取得数据库写锁后两次检查顶层普通文件身份和SHA-256，识别期间发生外部替换时拒绝入库并保留恢复旁证。新原件落盘前建立唯一小型`.upload-pending`标记，写锁持续繁忙、二次校验失败或提交结果不确定时由启动恢复器按精确路径/物理文件及SHA-256判断无引用原件清理或已入库原件确认；同SHA但不同路径不算当前原件引用。该锁保证删除不会与识别、确认或相同文件重传交错；前端上传、Sol和删除互斥只作为用户操作层补充。

官方依据：[Codex App Server](https://learn.chatgpt.com/docs/app-server) 支持ChatGPT管理登录、账户额度、模型列表、图片输入和本地 `stdio`；[GPT-5.6 Sol模型页](https://developers.openai.com/api/docs/models/gpt-5.6-sol)确认其模型ID、图片输入及结构化输出能力。模型和订阅可用性以运行时检查为准。

## 账单确认、余额与Settlement数据链

- `POST /api/statement-imports/{id}/confirm`是唯一正式入账入口。它在同一数据库事务中保存人工确认值和持仓，建立`source_type=STATEMENT_IMPORT`且带`statement_import_id`的BalanceSnapshot，把`confirmed_account_id`、`confirmed_snapshot_id`写回StatementImport，并记录`STATEMENT_CONFIRMED` AuditEvent。
- 原始Statement Import文件通过`statement_import_id`构成Snapshot来源证据；StatementImport保留本地OCR、Sol或历史Luna候选、人工值及修订轨迹。确认结果页和资金页据此显示原账单、账户及Snapshot关系，不复制或重写原始文件。
- `DELETE /api/statement-imports/{id}`允许删除正常未确认记录；已确认误入账须提交去空格后2至500字符原因，并要求Statement Import与唯一Balance Snapshot在`confirmed_account_id/confirmed_snapshot_id/statement_import_id/source_type/account_id`上双向一致。任意SettlementAccountLine、规范化Statement/Snapshot Attachment或ExportRecord、`duplicate_of`后继、相同路径/物理文件共用，以及确认原件缺失、为空、非普通文件、越界或SHA-256不一致均返回409。未确认记录若原件本来不存在可删除数据库记录，但现存原件同样必须通过路径、类型和哈希检查。
- 已确认删除在`BEGIN IMMEDIATE`事务内用Core SQL删除对应Balance Snapshot（持仓按已定义关系清理）和Statement Import，保留Client/Sub Account，并写`entity_id=NULL`的最小化撤销审计。审计保留原因、原ID、原文件名、Snapshot最小摘要和哈希证明，不复制持仓明细、OCR文本或AI响应；因此它是受控最小留痕，不应表述为完全去敏。
- 原件在数据库提交前先同目录原子改名为唯一`.delete-pending`文件；提交失败恢复原名，提交成功后再unlink。unlink失败返回pending并追加审计。数据库初始化后、开始服务前的恢复器只处理顶层严格命名的`.delete-pending`及`.upload-pending`旁证：删除旁证在仍有匹配数据库记录时恢复，无记录且有唯一已提交删除审计时清理；上传旁证在唯一数据库记录已引用完整原件时只清标记，无引用时清理本次孤儿原件和标记。`statement_imports`根目录为链接/重解析点、同一原件存在多个旁证、路径/哈希冲突、数据库直接引用pending或证明不唯一时停止启动。
- 相同Account Number可存在于不同Platform。确认时若账号只匹配一个Sub Account可自动采用；多条候选只有在Scheme唯一匹配时可自动采用，否则返回409并要求明确选择。所有账户选择项使用Client、Platform、Account Number和Scheme共同标识；复核页切换导入记录会清空旧选择，显式选择时请求同时携带并由后端核对`account_platform_id`。
- `GET /api/transactions`只读扩展返回Client、Platform、Fee Plan和Scheme身份字段；`GET /api/balance-snapshots`除同组身份外还返回`statement_import_id`与`holdings`。Settlement账户行和Invoice账户行的只读响应也返回`scheme_name`，其中Invoice的Scheme明确标为当前Sub Account主资料参考，Fee Plan及已冻结Platform/Account Number/期间/Service Fee仍是正式账单依据。该组只读字段是0.2.12行为；0.2.14另有Settlement版本和付款台账Alembic迁移，但不改变Scheme仍是当前资料参考的口径。
- BalanceSnapshot只表示一个Sub Account在一个日期的余额。确认余额页不会创建TransactionRecord；供款记录、资产转入记录和累计净供款也不会自动映射为Contribution/Withdrawal。资金流水必须由财务单独选择账户、日期、类型和金额后登记并关联凭证。
- 导入Snapshot只有在日期为季末或等于该账户实际`end_date`时才自动获得Closing资格；其他日期只作普通快照。若确认时建立DRAFT Client/Sub Account，须补齐Company、FC、Platform、Fee Plan、开始管理日期及适用的实际结束日期并激活；ACTIVE写入及季度结算均拒绝缺少`start_date`的遗留账户。账户`end_date`变化时，若新日期早于该账户任何未作废Settlement的Closing Date立即409拒绝；通过后再重算未被Settlement引用的导入Snapshot资格。手工Snapshot保留人工False选择，只会在原True不再符合规则时降级；若资格变化会触及已引用Snapshot同样409拒绝，并记录审计。
- Statement确认不会自动建立、Calculate或Finalize QuarterlySettlement。结算页通过Balance Snapshot只读列表提供候选；财务逐账户选择期间、Beginning/Closing Snapshot及首次Original HWM后调用Calculate保存Draft。Finalize的第一条数据库语句取得SQLite `BEGIN IMMEDIATE`写锁，再由共享计算服务从当前数据库重查账户状态、冻结归属、费率、Snapshot、Transaction、前序HWM及同账户同季度冲突，并逐字段比对已存Draft；差异返回409，不静默改写旧Draft。内部Excel候选和历史Settlement列表从`account_lines`及账户只读资料逐行显示Sub Account号码与Scheme。Calculate与Finalize均要求Client及所有Sub Account仍为ACTIVE且账户具有开始管理日期，防止未确认、资料不完整或已关闭账户被正式锁定。历史表及结果同时显示`version_no`、直接替代来源和VOID原因；最新版本VOID后Calculate只建立下一连续版本，不原地复用。
- 凭证关联目标是受控状态；切换Snapshot/Transaction类型或Client、Platform、Sub Account筛选即清空旧ID。前端不得把一个实体类型下的旧数字ID与另一类型组合提交，避免错误满足Finalize凭证门槛。Finalize会对每个StatementImport/Attachment检查受控数据根、普通文件、非空、登记大小（如适用）及SHA-256；SQLite Trigger同时禁止在相关Settlement仍为Finalized时删除或改写证据关系，Void后才开放底层纠正。

## 计算公式

- Net Contribution = Contribution - Withdrawal
- Gain/Loss = Closing - Beginning - Net Contribution
- Period Rate = Gain/Loss / (Beginning + Net Contribution)
- Adjusted HWM = Original HWM + Net Contribution
- Watermark Difference = Closing - Adjusted HWM
- Service Fee = MAX(Watermark Difference, 0) × Fee Rate
- Next HWM = MAX(Adjusted HWM, Closing)

Days只展示，不参与收费。0.2.19结算流水口径是`transaction_date > beginning_snapshot.as_of_date AND transaction_date <= closing_date`。自然季度首日开始时，首次Beginning允许等于Starting Date，或等于紧邻的上一季末；前者代表当天资金已包含在Beginning中，后者使季度首日资金进入Net Contribution。非季度首日仍只能使用Starting Date当天Snapshot；后续期间继承上一期Closing Snapshot。数据库冻结口径继续使用`>= start_date`，因此期间内流水在Finalize后均不可增删改。Finalize时逐Sub Account重新核对前序SettlementAccountLine/Next HWM，并保存固定公式版本、费率、账户构成、Company/FC归属及结果快照。HWM链只能按时间向后锁定、按时间倒序作废。

SQLite Trigger为避免精确PPM校验中的64位整数运算溢出，要求Beginning、Net Contribution和Gain/Loss三项各自的绝对值均不超过`9,000,000,000,000` cents（HKD 90,000,000,000）；任一项超过即停止迁移或Finalize并要求专门的高精度迁移。这是SQLite整数实现上限，不是收费业务上限，也不得被前端解释为客户额度。

Draft仅可通过`DELETE /api/settlements/{id}`删除，账户行由同一事务级联清理并写`SETTLEMENT_DRAFT_DELETED`审计；Finalized及Void明确拒绝。Finalized可从季度结算页面受控Void，但仍须先处理活动Invoice来源并按账户HWM依赖倒序操作。VOID历史继续保留原版本及明细；同自然键只对非VOID记录实施活动唯一，下一次Calculate建立`version_no + 1`并以唯一`replaces_settlement_id`指向最新VOID。应用及Trigger共同拒绝跨自然键替代、非连续版本、替代非VOID记录、同一旧版本被多次直接替代或并发建立两个活动版本。

## 完整数据包导入导出不变量

- 导出使用SQLite Backup API，并在写ZIP前验证副本的`integrity_check`、`foreign_key_check`、金融系统核心表/列及当前Alembic revision；数据库目录、数据库文件及业务文件树中的symlink/junction一律拒绝。年度、季度仅写入Manifest的`snapshot_period`作为复核批次标签，不参与SQL或文件筛选。ZIP先写入同一备份目录的唯一临时名，按完整导入规则自校验后以不覆盖的同目录原子`rename`公布；同秒或并发请求各自得到不同成品路径。
- 新Manifest格式为`financial-fee-system-data-package`版本1，只允许精确相同`app_version`和当前revision `d4f8a1c73b29`导入。校验要求唯一键JSON、受控相对路径、ZIP普通成员、Manifest精确字段、归档文件全集、逐文件SHA-256及唯一数据库；除Payment/PaymentRefund凭证和Statement Import原件外，0.2.17还逐笔核对全部Attachment、ExportRecord和Invoice中英文PDF。数据库SHA-256、Manifest SHA-256和实体内容必须相等，缺失、篡改、孤儿、`.delete-pending`/`.upload-pending`及数据库副本/文件复制竞态均拒绝。旧`financial-fee-system-backup`版本1继续按历史head契约识别，但不提供跨数据根路径重定向保证。
- 导入是整库及四类业务文件目录的完整覆盖，不做合并。不同电脑的数据根不同时，只在待导入SQLite副本内重定向`statement_imports.stored_path`、`attachments.stored_path`、`export_records.stored_path`和`invoices.pdf_paths_json`；精确三项证据保护Trigger在同一事务内临时撤下并按原SQL恢复。修改后更新临时Manifest数据库哈希，并再次验证数据库身份、`integrity_check`、外键、57个Trigger及全部文件路径/哈希，任一步失败均不得触碰接收方活动资料。
- HTTP中间件以导入专用读写门闩跟踪API财务写请求：普通写入保持既有并发能力并增加活动计数，导入只在活动计数为0时独占进入，进入后新的写入直接409；导入上传再从读取前使用专用非阻塞进程锁，第二请求同样409。已验证pending树保持为不可变源；marker写入后中间件拒绝除安全退出外的全部API写入，响应完成后由ShutdownCoordinator自动优雅停机，防止排队后新增数据在重启时被数据包覆盖。系统下次启动在数据根同一卷的`tmp`中预制`database/attachments/statement_imports/output`四个完整目录并再次验证，再通过持久化journal和同盘目录`replace`切换；普通异常逆序回滚，进程中断由下次启动依据`preparing/applying/rolling_back/committed`恢复，完成前不会启动数据库服务。
- `committed`是不可逆点；marker、pending和旧目录清理由幂等收尾完成，失败只明确告警并保留journal供后续启动重试，不得把已成功恢复报成失败或回滚成混合代际。后续新恢复marker不会被旧committed事务误删。无引用旧pending及上传ZIP会在启动时按安全前缀重试清理。

## Invoice聚合与恢复不变量

- Draft由服务端按Client、年度、季度和Fee Plan查询全部Finalized Settlement，不接受前端提供金额或可选择来源；总额以各冻结账户行的整数分相加。候选、已选组合和Invoice明细必须显示Fee Plan，账户行同时显示`Scheme（当前资料）`供人工辨认具体Sub Account。
- 零收费Settlement仍进入来源和明细；只有整组总额大于0才生成Invoice。组内冻结Company/FC必须一致，不一致即拒绝合并。
- 同一客户季度计划最多一张Draft/Issuing/Issued Invoice，同一Settlement最多一个active InvoiceSource；Invoice Void由数据库触发器把全部来源置为inactive。OPEN Invoice Correction会阻止同组从旧Settlement直接重开，替代Invoice只能在原Settlement逐一形成完整`replaces`版本链后建立。
- Issue前应用及数据库触发器都重新确认同组Finalized来源全集、来源金额、逐行金额和Invoice总额一致。Draft建立后新增的迟到Settlement会阻止签发，必须作废重建。
- SQLite只允许`DRAFT→ISSUING/VOID`、`ISSUING→ISSUED/DRAFT`和`ISSUED→VOID`；离开Draft后金额、分组、Company/FC、Fee Plan和兼容Anchor不可修改，编号及Issue/Due Date只能在预留时写入或ISSUING退回Draft时清空。Source/Line不能跨Invoice改挂。
- Invoice PDF只使用Invoice冻结的Company/FC关系及InvoiceLine账户、期间、Service Fee，不从Client当前Company/FC重新推导，也不把跨Platform合并扩散到HWM计算。0.2.18模板把Fee Plan名称作为服务说明，客户PDF不输出InvoiceLine内部冻结的Platform，也不输出Trustee、Platform Code或当前Scheme；Platform及Scheme仍在签发前页面供内部辨认，底层来源与冻结关系不变。若未来要求历史账单永久保留Scheme名称，必须另做Schema迁移和冻结规则。
- Invoice编号为`Company全名-中介人名字缩写-IssueDateYYYYMMDD-N`。Company Code不参与编号；`N`按Company+FC持续递增且不按日期或格式切换重置，历史编号不改写。
