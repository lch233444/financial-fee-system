# 金融计划收费计算系统 · 用户操作手册

适用版本：**0.2.20**。文档修订：**2026-09-07**。

本手册按当前页面说明财务操作。完整业务规则、技术依据及实现差距见[项目说明书](项目说明书.md)。本次只更新说明，当前程序仍存在第6节列出的三处问题。

## 1. 启动、数据目录和退出

完整保留`FinancialFeeSystem`运行文件夹，双击其中的`启动金融计划收费系统.bat`或`FinancialFeeSystem.exe`；不能只复制EXE或直接在ZIP内运行。

首次启动选择业务数据目录。程序目录、源码和业务数据分开；本机正式目录登记见[版本基线](项目说明书.md#state)。不要在开发版中选择正式数据目录。若8000端口已占用，应先核实已有程序，不能连续启动多个版本。

浏览器地址通常为`http://127.0.0.1:8000`。使用结束点击左侧底部“安全退出系统”，等待退出提示；只关浏览器标签不会停止后台服务。不要在程序运行时手工移动数据库、附件或归档文件。

## 2. 首次设置和完整账户身份

1. 在“基础设置”依次建立Company、FC、Platform及Fee Plan。Company填写全名、内部Code、收款/支票资料及默认付款天数；FC填写所属公司和中介人名字缩写。
2. 当前实际计划只有“利润20%”，费率20%。不要把技术上可配置其他费率理解为已经批准其他计划；Defer当前不使用。
3. 在“客户与账户”建立Client，明确Company、FC及Management Start Date；为每个Sub Account填写Platform、Account Number、Scheme、Fee Plan、开始管理日期和适用的实际结束日期。
4. 确认资料完整并激活。导入时自动建立的DRAFT Client/Sub Account须分别补全后才能进入正式季度结算。

选择账户时始终同时核对 **Client、Platform、Account Number和Scheme**。不同Platform可以出现相同号码，仅看Account Number可能挂错账户。FC是客户介绍和服务归属人，收款主体是Company。

误建主资料只在没有后续引用时允许删除。账户有流水、快照或结算等资料时会被拒绝，不能删除上级资料来连带清空业务。

## 3. 账单导入与人工确认

### 3.1 上传及本地识别

进入“账单导入”，上传JPG、PNG或PDF，单文件不超过25MB。系统优先读取PDF文字层，其他图像使用本地OCR。本地扫描PDF超过20页时只处理前20页并显示警告，剩余页须人工核对，不能认为整份已识别；Sol超过20页时要求拆分后再处理。本地OCR不把账单上传外部服务。

系统区分账户余额页、供款/资产转入等非余额凭证和未知文件。累计净供款、累计投资盈亏仅作参考，不是本季度流水或收益。文件完全重复时返回既有记录；语义重复提示需要财务核对。

### 3.2 可选Sol辅助识别

首次使用先在“数据与系统”点击“登录ChatGPT Pro”，在浏览器为本系统专用环境完成本人账号授权。登录与桌面Codex分开，不能复制桌面登录文件。系统显示识别就绪后，在导入记录上点击“运行Sol辅助识别”。

该操作会把当前账单图片发送给OpenAI，固定使用`gpt-5.6-sol`识别一次。它不自动改用第二个模型。未登录、额度不足、组件异常、超时或结构校验失败时保留本地OCR，改由人工复核。

OCR和Sol结果分别显示：一致值也只是候选；冲突、缺失或不确定项必须逐项核对。已经确认入账的记录不能重新识别；已有Sol比对结果后也不能重新运行OCR来改变原比对基线。

### 3.3 复核和入账

1. 查看原件，核对客户姓名、账户号码、Platform/Scheme、币种、As-of Date、Total Balance及持仓；必要时修订候选值。
2. 明确选择完整Sub Account身份。切换导入记录后重新核对所选账户，不沿用上一条选择。
3. 冲突/不完整项按页面要求逐项人工确认。只有本地分类未知、Sol明确为有效余额页时，才可在查看原件后额外勾选采用文档类型；本地已确定为供款类时不能强行作为余额页入账。
4. 账户不存在时可建立待补全资料；关键字段缺失或格式非法时不能确认。
5. 确认后检查页面显示的Client、Platform、Account Number、Scheme、Snapshot日期/金额、持仓、Closing资格及Snapshot编号。

确认仅建立该账户的 **Balance Snapshot日余额快照**，并保留原件、识别值、人工值和来源关系。它不会自动登记Contribution/Withdrawal，也不会Calculate或Finalize。非季末且非实际退出日的快照只能作为普通余额记录。

补录账户结束日期时，系统可重核未锁定导入Snapshot的退出日资格；若日期早于已有未作废结算的Closing，或影响已被结算引用的Snapshot，会拒绝保存。

### 3.4 导入错误的撤销

未确认记录可点击删除并再次确认。现存原件及识别结果随记录删除；确认痕迹、重复后继、Snapshot关系或原件异常时拒绝操作。

已确认误入账须填写2至500字符原因并再次确认。只有它与唯一Snapshot来源一致、未被**任何状态**Settlement使用、无附件/导出/后继重复记录引用，且原件完整时才能撤销。成功后删除该次Snapshot、持仓、原件和识别结果，保留审计及Client/Sub Account。即使引用它的Settlement已VOID，也不因此获得删除资格。

删除期间不要并发上传或运行识别。提示“原始文件待清理”时安全退出后重启；仍异常则停止并交由开发者检查，不手工删除pending文件。

## 4. 资金与余额

“资金与余额”可按Client、Platform及Sub Account筛选。Snapshot记录某日余额，Contribution/Withdrawal记录明确日期的现金变化；两者用途不同，不会互相自动生成。

登记余额时选择正确账户、日期和金额并提供依据。由导入确认生成的Snapshot有Statement Import来源及原账单入口；手工Snapshot需相应凭证。只有合格季末/实际退出日Snapshot能选作Closing。

登记资金流水时，明确Sub Account、生效日期、Contribution或Withdrawal、正数港币金额和备注，并上传关联凭证。不要把账单上的累计供款直接当作本期供款。

未被结算锁定的错误流水可点击“更正”，修改日期、类型、金额或备注并填写2至500字符原因。原Transaction ID与凭证保留，更正前后内容进入审计；无变化不会重复提交。更正后重新Calculate相关Draft。

已Finalize期间通常会拒绝直接更正，但当前跳季保护不完整，不能利用页面仍允许修改来改变已经参与正式收费的流水。普通流水删除/冲正、手工Snapshot及普通附件的完整更正/删除尚未提供。

## 5. 季度结算与核对

1. **先补齐前序季度。** 已有Q1而缺少Q2时，先完成Q2再结算Q3。当前程序仍可能允许跳季，财务必须执行该顺序。
2. 选择Client、Platform、Fee Plan、年度和季度，逐账户核对实际管理起止日期。
3. 每个账户选择合格Closing Snapshot。首次结算选择明确Beginning Snapshot并填写有依据的Original HWM；后续应继承上季度Closing和Next HWM。
4. 核对实际资金区间：从Beginning Snapshot日期之后起算，包含Closing当日。若Q2期初选择3月31日快照，4月1日流水需要计入；若选择4月1日当日快照，当日资金已在Beginning中，不重复计入。
5. 点击Calculate，逐账户复核Beginning、Closing、Contribution、Withdrawal、HWM、Service Fee及原件，再检查合计。各账户收费独立相加，不能用其他账户亏损抵销。
6. 缺资料或凭证时可保存Draft；核对完整后再Finalize。Period Rate分母为0显示N/A，不能正式锁定。

来源改变后Finalize可能要求重新Calculate；先核实变化，不重复点击试图绕过。Finalize锁定结果，但当前首日流水凭证复验仍有遗漏，见下一节。**Calculate/Finalize成功不替代财务对原件的核对。**

更正Finalized Settlement时，先处理活动Invoice；有现金或需保留替代关系的错单从Invoice发起Correction。再从HWM链最晚一期倒序操作“作废Settlement”，填写原因并确认。活动Invoice来源或后续结算依赖未解除时会拒绝。

旧记录保持VOID，按同一分组重新Calculate形成下一版本。版本号、旧ID和替代关系不能手工修改；新版本复核并Finalize后才进入替代Invoice。

## 6. 当前已知问题及操作限制

| 问题 | 当前操作要求 |
|---|---|
| F-01：采用前季末Beginning时，季度首日流水凭证文件损坏仍可能Finalize | 单独核对季度首日流水及原件完整性；发现原件异常停止Finalize，不能以“系统通过”为依据 |
| F-02：跳过Q2后，已用于Q3收费的Q2流水仍可能被修改 | 必须逐季度补齐；已出现跳季或来源被改时停止继续更正和开票，由开发者按原记录评估处理，不再修改历史输入试算 |
| F-03：已签发账单后新增遗漏平台，更正可能无法建立替代Invoice | 遇到“完整替代版本链”拒绝时保留原单、更正和新增来源，停止操作并报告；不删除来源、不另开第二张活动季度单、不直接改数据库 |

上述问题已用合成数据复现，文档更新尚未修复程序。详细原因和复现条件见[项目说明书的已知问题](项目说明书.md#gaps)。

## 7. Invoice签发与收款

### 7.1 建立和签发

在“Invoice与收款”按Client、年度、季度、Fee Plan建立Draft。系统自动纳入同组全部Finalized Settlement，可跨Platform；核对完整账户、Platform、Scheme、Fee Plan、期间和金额，不能选择性遗漏。全组Company/FC归属必须一致，总额须大于0；零收费来源也属于完整来源。

签发前核对Company全名、FC缩写、客户资料、Issue Date、Due Date、逐行费用及付款资料。编号在Issue时生成，形如`甲公司-TW-20260907-1`；序号按Company+FC持续递增，不每天重置。已有编号不会因公司名称后改而重写。

客户PDF显示账户号码、期间、服务说明和港币金额，不显示Platform/Trustee；内部核对仍有这些身份资料。Issue会保存中英文PDF，以后读取原归档。

Draft之后补出新Finalized来源时，按提示Void旧Draft再建立完整单。Issued后出现迟到来源需更正，新增平台的当前限制见第6节。

异常退出留在ISSUING时，使用页面恢复区：只有完整双语归档才能“完成签发”；否则“退回Draft”。两种处理都保留已消耗编号和审计。PDF缺失或哈希异常交由开发者检查，不能覆盖原归档。

### 7.2 一次性确认收款

在Issued Invoice的“PDF、付款与更正”区：

1. 填写实际收款日期、实际现金金额及非空方式。
2. 公司确认承担小额差额时填写金额和原因；为0时不填原因，差额不是现金收入。
3. 上传完整、未认领的付款凭证。
4. 核对 **实际现金 + 公司承担差额 = Invoice金额** 后提交。

当前不接受部分付款、第二笔付款或重复确认；成功后付款、分配、差额和凭证锁定。业务付款状态只有未付款/已付款，逾期是单独提示。不要用虚构收款补平差额。

### 7.3 错单更正、退款和公司承担差额

已收款错单点击“发起更正”，填写2至500字符原因。原Invoice转VOID但保留编号/PDF，原Payment保留；系统冲回现金分配，不删除或新造现金。

按第5节处理原Settlement并建立、Finalize完整替代版本，再建立并Issue同组替代Invoice。OPEN更正中的替代单保持资金空白，不先登记新Payment，也不再次发起Correction。

在更正完成区域选择替代Invoice，对每笔原Payment填写“保留分配”和“退款”。二者等于本轮可处置金额；退款大于0时填写日期、方式、原因及退款凭证。保留现金合计加公司差额必须等于替代Invoice金额。

| 情形 | 应填写的内容 |
|---|---|
| 原收120，正确应收100 | 保留100、退款20并提供退款凭证；不再新增100收款 |
| 原收100，因本公司计算失误更正为应收120 | 保留100、退款0、公司承担差额20，并说明计算失误原因；客户不补款，也不新增20现金 |
| 原单尚未收款 | 完成更正仅建立替代关系，新单保持未付款；不要在该完成步骤填写虚构付款或公司差额 |

金额巨大或不属于已确认的小额处理情形，由负责人另行决定，不能理解为系统自动批准任意减免。

连续更正必须先完成上一轮，再从当时的Issued替代单发起下一轮。下一轮只处理仍留存的现金，已退款金额不再分配。原收款、原编号和每轮退款记录应始终可追踪。

## 8. 导出与经营概览

内部Excel/Settlement PDF从Finalized结算导出。Excel沿用公司唯一母版，按Sub Account显示身份、期间和锁定费用；不要修改母版作为日常操作。客户Invoice PDF与内部结算文件分别使用对应入口。

“经营概览”按所选结算年度季度查看汇总。FC只统计当前管理客户数、本季度收费客户数和Service Fee，不是FC收款业绩。总额异常时回查账户明细、结算期和冻结归属，不通过改汇总数修正。

## 9. 完整数据包与换机

### 导出给复核人员

在“数据与系统”选择年度季度并导出完整数据包。这只是复核批次标签，包内始终包含导出时**全部**资料、账单原件、附件、付款/退款凭证及系统生成文件，不只包含该季度。

数据包含敏感客户资料，应通过有权访问的受保护渠道单独交接，不放入Git、程序源码或公开演示文件。

### 接收和恢复

1. 发送方和接收方使用完全相同系统版本；新电脑完整解压运行文件夹并选择数据目录。
2. 接收方如已有资料，先导出可恢复的现状数据包并确认本次整体覆盖。导入不会合并两边资料。
3. 在“数据与系统”导入数据包，阅读覆盖提示并确认。
4. 校验成功后等待系统安全退出，重新启动完成替换；不要并发导入、反复点击或手工处理数据库文件。
5. 重启后由有权人员复核客户/账户、原件、附件、结算、Invoice、收款及退款等是否与发送方导出时一致。

新数据包支持不同盘符和数据目录，系统在暂存副本中重定向路径并复验。旧格式备份不具备同样的跨路径保证，季度交接应从同版本系统重新导出新包。

版本不符、缺文件、哈希异常或恢复失败时停止，保留原资料和错误信息。不要改Manifest、复制单独SQLite文件或删除恢复日志来强行导入。系统专用ChatGPT登录不随业务数据包迁移，新电脑由本人重新授权。

## 10. 常见提示

| 提示/现象 | 处理 |
|---|---|
| 账户或客户未Active、资料不全 | 到“客户与账户”分别补齐并激活，核对管理日期 |
| Closing Snapshot不合格 | 核对账户、Snapshot日期、季末/实际退出日资格，不手填金额绕过 |
| Draft过期、来源已变化 | 核实更正内容后重新Calculate，再复核费用 |
| 缺凭证、文件大小或哈希不符 | 核对原件及关联，不把Finalize成功视作全部文件完整的保证 |
| 同组出现新Finalized来源 | Draft作废重建；Issued按更正处理，新增平台受第6节限制 |
| 替代版本链不完整 | 核对原来源替代关系；涉及新增平台时停止并报告F-03 |
| 现金与公司差额不等于应收 | 核对实际到账及已批准差额，不登记虚假Payment |
| 原始文件待清理/恢复未完成 | 安全退出后重启；仍异常则停止，不删pending或journal |
| Sol未就绪或识别失败 | 核对系统专用登录，保留本地OCR并人工复核，不反复调用其他模型 |

本手册随实际页面和业务规则同步维护。发现手册与程序不同，应保留错误信息并依据主说明书区分已知缺口和新问题。
