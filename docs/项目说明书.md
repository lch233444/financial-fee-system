## 1. 一页接手摘要

### 1.1 项目是什么

这是一个Windows本地运行的金融计划收费管理系统，用于把依赖Excel的季度收费流程转成可审计的工作流：

```text
基础资料
  → eMPF账单导入与人工复核
  → 账户余额和资金流水
  → 季度High Water Mark结算
  → Invoice签发
  → Payment登记
  → FC统计、Excel/PDF导出
  → 完整备份与恢复
```

系统的第一原则是财务准确与人工最终确认，不是追求无人值守。OCR和Luna都只能产生待复核候选值，不能直接写入正式财务链路。

### 1.2 当前交付状态

| 项目 | 当前状态 |
|---|---|
| 源码基线 | 0.2.2 |
| 运行形态 | Windows PyInstaller `onedir`完整目录；同时支持源码开发模式 |
| 前端 | React 19、TypeScript 5.9、Vite 7 |
| 后端 | Python 3.12、FastAPI、SQLAlchemy 2、Alembic |
| 数据库 | SQLite，启用外键、WAL、`synchronous=NORMAL` |
| OCR | 本地Tesseract；JPG、PNG、PDF文字层、扫描PDF多页、长截图分段 |
| AI辅助 | 用户主动触发；独立ChatGPT登录；固定 `gpt-5.6-luna` 单次识别 |
| 最新源码回归 | 后端91/91通过；前端TypeScript与Vite生产构建通过 |
| GitHub | 私有仓库仅保存脱敏源码、测试、模板和文档 |

0.2.2已经完成5类授权样本的OCR/Luna交叉评估。该评估只能证明当前小样本表现，不能解释为“任意客户账单通用准确率”。

### 1.3 新工程师前15分钟

1. 阅读根目录 `AGENTS.md`、本文件和 `docs/CHANGELOG.md`。
2. 运行 `git status --short --branch`，确认没有覆盖用户未提交的工作。
3. 运行 `./scripts/setup-dev.ps1` 安装锁定依赖。
4. 运行 `./scripts/start-dev.ps1`，确认前端 `127.0.0.1:5173` 与后端 `127.0.0.1:8000/api/health`。
5. 运行后端测试与前端生产构建，建立本机基线。
6. 只使用仓库内忽略的测试数据目录；不要复制或打开真实客户数据来“熟悉项目”。
7. 修改前先定位对应路由、服务、模型、测试和本文相关章节；优先最小变更。

## 2. 业务边界与非目标

### 2.1 当前用户与运行边界

- 当前MVP面向单台Windows电脑上的财务人员。
- 操作界面为中文，保留Beginning、Closing、HWM、Service Fee、Invoice、Payment等常用英文财务术语。
- 后端只能监听 `127.0.0.1`、`localhost` 或 `::1`。
- 当前没有用户登录、角色权限、多人并发或公司服务器部署。
- 业务数据由用户选择本机数据根，与源码、运行包和Git仓库分离。

### 2.2 已实现范围

- Company、FC、Platform、Fee Plan、Client、Sub Account基础资料。
- Contribution/Withdrawal、Balance Snapshot与账户附件。
- eMPF账单分类、本地OCR、Luna辅助识别、交叉核验、人工确认与审计留痕。
- 多账户组合的季度HWM计算、Draft/Finalize/Void与HWM继承。
- Invoice Draft/Issue/Void、连续编号、中英文归档PDF、多笔Payment。
- Dashboard、FC统计、内部Excel、客户结算PDF、完整备份与延迟恢复。
- Windows一键运行包、首次数据目录选择、页面安全退出。

### 2.3 未实现或不能声称已完成

- Defer延付利息计算。
- 自动邮件发送、用户权限、多人协作、服务器/局域网部署。
- 任意版式OCR、网页自动抓取、历史批量导入、模板版本管理。
- 定时备份、备份加密、完整数据保留与删除政策。

## 3. 系统架构

### 3.1 运行拓扑

```text
┌─────────────────────────────────────────────────────────────┐
│ Windows本机                                                  │
│                                                             │
│  浏览器 / React SPA                                          │
│          │ HTTP + X-Financial-System-Request                 │
│          ▼                                                   │
│  FastAPI（仅loopback）                                       │
│    ├─ SQLAlchemy/Alembic ── SQLite                           │
│    ├─ 文件服务 ─────────── 账单/附件/Excel/PDF/备份          │
│    ├─ Tesseract ────────── 本地OCR，不上传                   │
│    └─ Codex App Server ─── 独立CODEX_HOME                    │
│                              │ 用户主动点击时才发送图片       │
└──────────────────────────────┼──────────────────────────────┘
                               ▼
                         OpenAI / gpt-5.6-luna
```

### 3.2 开发模式与发布模式

| 模式 | 前端 | 后端 | 数据根 | 用途 |
|---|---|---|---|---|
| 开发模式 | Vite `127.0.0.1:5173` | Uvicorn `127.0.0.1:8000` | 默认仓库内 `data/` | 日常开发和自动化测试 |
| Windows发布模式 | 构建后的静态资源由FastAPI托管 | PyInstaller打包进EXE | 首次启动由用户选择 | 财务人员日常使用 |

发布模式必须保留整个 `FinancialFeeSystem` 文件夹，不能只复制EXE。启动器在导入数据库模块前确定数据根，避免SQLite连接到错误位置；端口8000被占用时启动直接失败，不会静默连接另一个实例。

```text

    models.py               ORM实体与数据库约束
    schemas.py              API输入校验与状态枚举
    serializers.py          Settlement/Invoice输出和付款状态
    money.py                分整数、Decimal及舍入工具

  src/types.ts              前端DTO类型
```

### 3.4 后端分层约定

- `routes/`：接收输入、加载关联对象、检查状态、控制数据库事务并记录审计。
- `services/`：放可复用的纯计算或外部集成，不应绕过路由层的财务状态检查。
- `models.py`：承担唯一键、外键和持久化约束，但不是所有业务规则的唯一位置。
- `schemas.py`：承担格式、范围和枚举校验；任何新增写接口必须复用或新增显式Schema。
- `serializers.py`：统一对外金额字符串和派生状态，避免前后端各自发明口径。

## 4. 领域模型与数据关系

### 4.1 核心关系

```text
Company ─┬─< FC
         ├─< FeePlan
         └─< Client >─ FC
                 └─< SubAccount >─ Platform / FeePlan
                       ├─< TransactionRecord
                       └─< BalanceSnapshot

Client + Platform + FeePlan + Year + Quarter
                 └─ QuarterlySettlement
                      ├─< SettlementAccountLine >─ SubAccount
                      └─ Invoice ─< Payment

StatementImport ──人工确认──> BalanceSnapshot
Attachment / ExportRecord / AuditEvent 为横向证据与审计记录
```

### 4.2 实体职责与关键约束

| 实体 | 职责 | 关键约束/自然键 |
|---|---|---|
| Company | 公司收款、支票资料和付款天数 | `name`、`code`唯一 |
| FC | Company内的财务顾问/渠道 | `(company_id, code)`唯一 |
| Platform | 计划平台/受托人 | `name`、`code`唯一 |
| FeePlan | Company内收费计划与费率 | `(company_id, code)`唯一；费率以bps保存 |
| Client | 客户及归属Company/FC | ACTIVE前必须有Company、FC、Management Start Date |
| SubAccount | 客户的平台账户 | `(platform_id, account_number)`唯一；ACTIVE前必须有Platform、Fee Plan |
| TransactionRecord | 账户级Contribution/Withdrawal | 金额必须大于0；日期参与季度区间汇总 |
| BalanceSnapshot | 某账户某日余额与持仓 | `(account_id, as_of_date)`唯一；Closing资格单独保存 |
| StatementImport | 原件、OCR、Luna、人工值和修订轨迹 | 文件SHA-256唯一；CONFIRMED后不可重新OCR/Luna |
| QuarterlySettlement | 组合级季度结算和HWM | `(client, platform, fee_plan, year, quarter)`唯一 |
| SettlementAccountLine | 结算内账户级Beginning/Closing | `(settlement_id, account_id)`唯一 |
| InvoiceSequence | Company+FC连续号码 | `(company_id, fc_id)`唯一；Void号码不回收 |
| Invoice | 正式收费单及归档PDF | 一个Settlement只能有一个有效Draft/Issued Invoice |
| Payment | Invoice收款明细 | 累计付款不能超过Invoice金额 |
| Attachment | 账户等实体的原始凭证 | 保存原名、存储路径、MIME、大小和SHA-256 |
| ExportRecord | Excel/PDF导出索引 | 保存文件路径、类型、语言和SHA-256 |
| AuditEvent | 关键状态变化审计 | 目前覆盖确认、Finalize、Void、Issue、Payment、AI识别等关键动作 |
| AppSetting | 预留的键值配置 | 当前不是主要用户配置来源 |

### 4.3 金额和费率类型

- 所有正式金额以HKD“分”的整数写入数据库，例如 `1234.56` 保存为 `123456`。
- 输入先通过 `Decimal(str(value))`，再以 `ROUND_HALF_UP` 量化至0.01。
- Fee Plan费率以basis points保存，20%为2000 bps。
- Period Rate以parts per million保存，API序列化时除以1,000,000。
- 禁止在新增代码中用二进制浮点直接累计财务金额。

## 5. 业务工作流和状态机

### 5.1 基础资料

1. 建立Company。
2. 在Company下建立FC和Fee Plan。
3. 建立Platform。
4. 建立Client并关联Company、FC。
5. 建立Sub Account并关联Client、Platform、Fee Plan。

Client和Sub Account都可先以DRAFT保存不完整资料。转为ACTIVE时后端再次校验必填关联；前端提示不能代替后端保护。当前PATCH接口允许在三个状态值之间更新，尚未强制单向迁移，因此调用方不能假设状态只能前进。

```text
Client/SubAccount状态值: DRAFT / ACTIVE / CLOSED
```

### 5.2 账单导入

```text
上传原件
  → magic bytes/25MB/哈希检查
  → 本地OCR与文档分类
  → NEEDS_REVIEW
  ├─ 可选：Luna单次辅助识别与交叉核验
  └─ 财务人工确认
       → CONFIRMED
       → 建立BalanceSnapshot
```

- 精确哈希重复直接返回原记录。
- 账户号+日期+余额相同属于语义疑似重复，保留记录但提示人工核对。
- 只有 `empf_account_page` 可以确认成Balance Snapshot。
- `contribution_record`、`contribution_asset_transfer_record` 和 `unknown` 在服务端硬性禁止入账。
- 若没有匹配账户，确认流程可以建立DRAFT Client/Sub Account；它们仍需补全资料才能ACTIVE。
- 季末或账户实际结束日的快照才标记 `eligible_for_closing=true`。

### 5.3 Settlement

```text
calculate → DRAFT → finalize → FINALIZED
              │                    │
              └──── void ──────────┴→ VOID
```

- 结算唯一边界是 `Client + Platform + Fee Plan + 年度 + 季度`。
- 同一结算中的所有Sub Account必须属于该组合。
- DRAFT可以重复calculate并替换账户明细。
- FINALIZED或VOID不能原地重算。
- 有Issued Invoice时，Settlement必须先处理Invoice，不能直接Void。
- Finalize写入时间并记录AuditEvent；公式版本和计算快照随后视为不可变。
- Void可作用于DRAFT或FINALIZED；当前接口未阻止对已VOID记录再次提交Void，属于待收紧的状态保护。

### 5.4 Invoice和Payment

```text
Invoice生命周期: DRAFT → ISSUED → VOID
                    └────────→ VOID
付款派生状态:    UNPAID / PARTIALLY_PAID / PAID / OVERDUE
```

- 只有FINALIZED且Service Fee大于0的Settlement可生成Invoice Draft。
- 编号在Issue事务中分配：`CompanyCode-FCCode-ClientStartYYYYMM-NNN`。
- `NNN`按Company+FC持续递增，不按月份重置，Void后不复用。
- Issue时同时生成中文和英文PDF并记录哈希；以后返回归档文件，不重新渲染覆盖。
- 有Payment的Invoice目前禁止直接Void。
- 部分付款优先显示 `PARTIALLY_PAID`；现实现不会额外叠加OVERDUE标签。

## 6. HWM计算规则

### 6.1 公式

```text
Net Contribution      = Contribution - Withdrawal
Gain/Loss             = Closing - Beginning - Net Contribution
Period Rate           = Gain/Loss / (Beginning + Net Contribution)
Adjusted HWM          = Original HWM + Net Contribution
Watermark Difference  = Closing - Adjusted HWM
Chargeable Above HWM  = MAX(Watermark Difference, 0)
Service Fee           = Chargeable Above HWM × Fee Rate
Next HWM              = MAX(Adjusted HWM, Closing)
Days                  = Closing Date - Starting Date + 1
```

### 6.2 不变量

- Days仅展示，不参与收费。
- Starting Date当天资金视为已包含在Beginning；流水区间为 `transaction_date > start_date && <= closing_date`。
- 首次Original HWM必须由财务输入，系统不能猜测为Beginning或管理起始金额。
- 后续Original HWM继承同一组合最近一期FINALIZED Settlement的Next HWM。
- Period Rate分母为0时返回N/A并禁止Finalize。
- Closing Snapshot若提供，必须属于对应账户、日期等于Closing Date、具有Closing资格且金额完全相等。
- Beginning/Closing保存在账户明细，HWM保存在组合结算级；不得跨客户、平台或Fee Plan合并。

改变公式、舍入、日期边界或HWM继承逻辑属于高风险业务制度变更，必须有用户明确确认、回归样例和文档同步。

## 7. OCR与Luna交叉核验

### 7.1 本地OCR流水线

`backend/app/services/statement_parser.py`负责：

1. 识别JPG/PNG/PDF真实格式。
2. PDF优先读取原生文字层；扫描PDF逐页渲染，最多20页图像OCR。
3. 长截图按重叠区域分段，减少窄列和超长表格遗漏。
4. 按版式关键词分类文档。
5. 提取客户、账户、计划、日期、余额、累计参考字段和基金持仓。
6. 生成字段置信度、警告、解析器名称与版本。

累计净供款和累计投资盈亏是lifetime参考，绝不能映射为本季度Contribution、Withdrawal或Gain/Loss。

### 7.2 Luna集成边界

`backend/app/services/codex_app_server.py`通过本地 `stdio` 使用Codex App Server：

- 不读取或保存OpenAI API Key。
- 使用应用专用 `FINANCIAL_CODEX_HOME`，不能指向用户桌面Codex的 `~/.codex`。
- 子进程环境主动清除外部 `CODEX_HOME`，并检查配置中没有插件、Hook、MCP或指令来源。
- 发送图片前检查ChatGPT认证模式、额度与精确模型可用性。
- 模型固定 `gpt-5.6-luna`，不接受前端覆盖，不升级到Terra/Sol，不调用第二模型。
- 每个导入记录只消费一次识别；并发点击通过进程内锁和幂等检查合并。
- 超时、额度、认证、协议、Schema、错误模型回执或静默重路由全部失败关闭，保留OCR并转人工。

### 7.3 比对和入账边界

OCR与Luna对标准化字段及基金名称匹配：

- `AGREED`：不存在冲突、缺失、不确定或不支持类型。
- `INCOMPLETE`：有单侧值、关键字段缺失、不确定字段或不支持文档类型。
- `CONFLICT`：双方标准化值不一致。

无论状态如何，`requires_financial_confirmation`始终为true。Luna接口只允许写StatementImport辅助字段和AuditEvent，不能创建或修改BalanceSnapshot、Transaction、Settlement、Invoice或Payment。确认时若存在冲突/不完整，财务必须显式勾选已逐项核对。

### 7.4 当前样本基线

2026-08-26的5份授权样本中：OCR文档分类5/5，Luna文档分类5/5；3份余额页四个关键字段OCR为12/12、Luna为10/12；两份非余额凭证均正确分流。完整条件、逐字段结果和改进建议见 `docs/客户账单OCR_Luna识别评估_20260826.md`。

真实样本测试会向OpenAI发送图片，必须获得用户对该文件的明确同意，且不得作为普通自动化测试自动运行。

## 10. 数据目录、迁移与备份

### 10.1 数据根结构

```text
<FINANCIAL_DATA_ROOT>/
  database/financial_system.sqlite3
  statement_imports/
  attachments/
  output/excel/
  output/pdf/
  backups/
  tmp/
  tmp/ai-codex/
```

Luna独立登录目录默认在 `%LOCALAPPDATA%/FinancialFeeSystem/LunaCodexHome`，不属于上述业务备份，也不得复制到Git或换机包。

### 10.2 数据库启动迁移

- 正常启动运行Alembic到 `head`。
- 对早期没有 `alembic_version` 的MVP数据库，先创建缺失表，再按已有列判断应从初始版本还是AI迁移继续。
- 该兼容路径用于保留旧数据，不代表可以跳过新增迁移文件。
- 任何模型变更必须新增Alembic revision；禁止只修改ORM后依赖 `create_all` 修生产库。

### 10.3 备份与恢复

- 备份通过SQLite Backup API取得一致数据库副本，不直接复制运行中的数据库文件。
- ZIP包含数据库、`attachments`、`statement_imports`、`output`和 `manifest.json`。
- Manifest记录每个文件的SHA-256。
- 恢复先检查ZIP路径穿越和逐文件哈希，再写入 `pending_restore.json`。
- 真正替换在下一次应用启动、数据库初始化前执行。

恢复会替换业务数据目录中的数据库和归档文件，属于高风险操作；开发者不得在没有用户明确授权与可验证备份时执行。

## 14. 安全和隐私不变量

- 客户账单、业务数据库、附件、导出、备份、登录状态和工具二进制不得进入Git。
- `.gitignore`是最后一道保护，不是提交前审查的替代品。
- 所有API写请求必须携带本地系统标记；Host和监听地址必须保持loopback。
- 文件上传验证大小、magic bytes、允许类型、安全文件名和存储边界。
- 文件下载前验证记录路径仍位于允许的数据根。
- AI识别必须用户主动触发；“无需API Key”不等于完全离线。
- 图片和OCR文本属于不可信输入，不能成为指令来源。
- Luna不得继承桌面Codex的AGENTS、技能、插件、Hook、MCP或认证目录。
- AI失败必须降级人工复核，不能升级模型、循环重试或自动胜出。
- 安全退出只停止本应用拥有的Codex/Luna子进程，不能枚举或结束用户其他Codex任务。
- Finalized Settlement、Issued Invoice和归档PDF必须保持不可变与可审计。

## 16. 故障定位速查

| 现象 | 首查位置 | 处理原则 |
|---|---|---|
| EXE启动失败 | `%LOCALAPPDATA%/FinancialFeeSystem/launcher-error.log` | 先读错误；不要重复覆盖运行目录 |
| 提示8000占用 | 检查是否已有FinancialFeeSystem实例 | 先用页面安全退出；不要杀其他Codex进程 |
| 页面仍是旧UI | `/api/health`版本、实际启动路径、浏览器缓存/静态资源 | 确认启动的是唯一正式目录 |
| OCR不可用 | `TESSERACT_CMD`、语言包、`tools/Tesseract-OCR` | 保留上传和人工复核，不伪造OCR结果 |
| Luna显示未登录 | `GET /api/ai-assistant/status`、独立登录目录 | 只登录本系统专用环境 |
| Luna模型/额度不可用 | 状态接口的model/quota/auth结果 | 转人工，不换模型、不自动重试 |
| 导入不能确认 | 文档类型、关键字段、重复、账户匹配、AI冲突确认框 | 以服务端错误为准逐项修正 |
| Settlement不能Finalize | 分母、账户明细、Closing资格、状态 | 不绕过校验直接改数据库 |
| Invoice不能建立/Issue | Settlement状态、Service Fee、Client资料、已有有效Invoice | 修复上游资料和状态 |
| PDF缺失 | Invoice归档路径和数据备份 | 从备份恢复；不要静默重生成覆盖已签发文件 |
| 恢复失败 | ZIP格式、Manifest、SHA-256、路径穿越检查 | 不手工绕过校验 |
| 数据库结构异常 | `alembic current/history`、迁移文件、旧库列 | 先备份并复现，禁止直接改生产库 |

## 17. 已知缺口与建议优先级

### P0：财务完整性

1. Settlement API允许不传 `closing_snapshot_id` 并手填Closing，可能绕过季末/退出日资格。
2. Beginning尚未关联明确的 `beginning_snapshot_id`，目前依赖人工输入。
3. Transaction和Payment凭证强制规则未完整接入，需要业务确认标准。
4. 有付款后的Invoice更正缺少退款、冲销和Credit Note流程。

### P1：报表与审计

1. FC统计按Settlement期间归集，不是Payment Date现金发生期；前端缺少期间选择。
2. 部分付款逾期只显示PARTIALLY_PAID，不额外标记OVERDUE。
3. AuditEvent前端不可查询，且并非所有普通资料修改都有完整事件。
4. Excel模板版本和导出契约尚无自动版本管理。
5. Settlement Void接口未阻止对已VOID记录重复提交，可能产生重复作废审计事件。

### P2：产品完整度

1. 多数基础资料、流水、快照和附件缺少完整更正/删除/冲正流程。
2. Company Logo字段存在，但缺少上传和配置界面。
3. 任意版式OCR、历史批量导入和浏览器E2E尚未实现。

优先级只是工程建议，不是用户已批准的开发排期。开始其中任何一项前，应确认当前用户目标和业务口径。

## 18. 不可随意推翻的工程决策

- SQLite和本地文件：符合当前单机隐私与低部署成本；服务器化必须另做架构评审。
- `Client + Platform + Fee Plan`结算边界：防止不同资金池/HWM互相污染。
- Beginning/Closing账户级、HWM组合级：同时保留凭证和收费口径。
- 首次HWM人工输入：系统缺少安全推断依据。
- OCR + Luna双通道、人工最终确认：效率不能覆盖财务责任。
- ChatGPT管理登录而非普通API：满足用户不新增API费用的要求，但受订阅与模型可用性影响。
- 单模型失败转人工：保证成本、可审计性和结果稳定。
- Issue时编号且Void不复用：保证账单审计链。
- Service Fee为0不生成付款Invoice：避免无应付款账单。
- 独立目录构建后再提升：避免端口占用、旧包运行和覆盖损坏。

## 19. Definition of Done

一项开发任务只有同时满足以下条件才算完成：

- 用户目标和业务口径已明确，未擅自扩展范围。
- 代码变化最小且遵循现有分层，没有绕过后端财务保护。
- 新增或修改行为有对应自动化测试。
- 数据库变化有Alembic迁移和旧库兼容验证。
- 金额、日期、状态、重复与失败路径均经过验证。
- 涉及真实图片/Luna时已取得云端上传同意，并单独报告真实验收范围。
- `docs/项目说明书.md` 与 `docs/CHANGELOG.md` 已同步。
- 后端测试、前端构建及风险相关的EXE/API/UI/导出验收已执行并报告结果。
- `git diff`中没有客户资料、凭据、二进制、构建输出或无关修改。
- 交付说明包含：改了什么、如何验证、是否触碰业务数据、遗留问题和Git提交状态。
