## 1. 当前基线、业务目标与角色

### 1.1 目标和范围

系统把人工Excel收费流程转为可核对、可锁定、可追踪的Windows单机工作流。财务人员无需安装Python/Node即可运行正式包，在浏览器操作并安全退出。

以下表格记录**0.2.30现有实现**。2026-09-12已确认的公司解绑目标见[第12节](#meeting-requirements)：Company仅作收款载体，在出具账单前选择；客户、FC、Fee Plan不再绑定公司。该目标尚未实施，表内现有绑定不得继续作为新制度要求。

| 角色/对象 | 0.2.30现有含义与约束 |
|---|---|
| Company | 向客户出具Invoice并实际收款；全名参与Invoice编号，Code仅作内部标识 |
| FC | Company内介绍客户并持续服务的中介人；现有`code`字段存名字缩写；不是收款人 |
| Client | 公司管理的客户，归属于Company和FC |
| Platform / Trustee | 账户所在计划平台及可选MPF受托机构；Trustee不是FC，不参与Invoice编号 |
| Sub Account | 独立账户身份、资金、余额、期间、HWM和收费的最小单位 |
| Fee Plan | 2026-09-10确认由用户添加并分配各账户的收费计划；沿用HWM利润收费公式，费率可配置，默认20%，不从文件名编码推导 |
| 财务/复核人员 | 财务负责核对原件并确认；季度复核人员通过同版本全量数据副本检查，不向主库合并修改 |

当前不开展Defer、服务器、多用户或权限体系。多Fee Plan同单已按2026-09-10确认实施；固定费用、分档费率、Defer等其他收费制度和服务器化仍须另行确认。当前中文界面保留Beginning、Closing、HWM、Service Fee、Invoice、Payment等业务术语；避免重复提示占据操作界面，必要边界写入操作语境和文档。

已确认移除的重复界面块包括导入页顶部OpenAI pill、识别卡片底部整条云上传提示，以及系统页重复云处理/不升级模型提示；后续不得仅为披露重复加回。图片上传事实仍须在主动操作语境和手册中清楚说明。

## 2. 领域模型、模块职责和数据流

### 2.1 运行结构

```text
浏览器 React/TypeScript
  └─ FastAPI /api（仅loopback，写请求标记）
       ├─ SQLAlchemy + Alembic → SQLite及Trigger
       ├─ 文件服务 → 账单原件、附件、Excel/PDF、数据包
       ├─ Tesseract → 本地OCR候选
       └─ Codex App Server stdio → 独立ChatGPT登录 → Sol候选
```

开发时Vite提供5173页面；正式版由FastAPI托管前端构建资源。PyInstaller采用onedir，必须保留整个程序文件夹。启动器先确定数据根再导入数据库；8000被占用时不应把另一个实例当作当前程序。

### 2.3 数据关系和关键约束

```text
Company → FC / FeePlan / Client → SubAccount → Snapshot / Transaction
StatementImport ─人工确认→ BalanceSnapshot ─人工选择→ SettlementAccountLine
Client + Platform + FeePlan + 年度季度 → QuarterlySettlement及账户明细
Client + 年度季度 → Invoice（跨Platform、跨FeePlan） → InvoiceSource / InvoiceLine
Invoice → Payment → PaymentAllocation（APPLY / REVERSAL）
原Invoice → InvoiceCorrection → 替代Invoice / PaymentRefund / InvoiceAdjustment
Attachment、ExportRecord、AuditEvent提供实体证据和追踪
```

| 实体 | 当前关键约束 |
|---|---|
| Company / FC / Platform / FeePlan | Company和Platform各自name/code唯一；FC、FeePlan的code在Company内唯一 |
| Client / SubAccount | 同一人一个客户档案、多个独立子账户；姓名不是唯一身份键。ACTIVE前补齐归属与管理日期；账户号码在Platform内唯一，跨Platform同号不能混用 |
| BalanceSnapshot | 同账户同日期唯一；保存持仓、来源及Closing资格；不是流水或自动结算 |
| StatementImport | 文件SHA-256唯一；保留OCR、AI候选、人工值和确认关系；CONFIRMED不能重新识别 |
| QuarterlySettlement | 自然键为Client/Platform/FeePlan/年度/季度；版本永久唯一，只有一个非VOID活动版本；替代外键唯一、RESTRICT |
| SettlementAccountLine | 同Settlement内账户唯一；逐账户期间、公式和Snapshot来源；`previous_line_id`为HWM前序 |
| Invoice / InvoiceSource | 同客户年度季度最多一张DRAFT/ISSUING/ISSUED；同Settlement最多被一张活动Invoice占用；`settlement_id`及`fee_plan_id`仅为首个来源的兼容锚点，不是发票分组或全单费率 |
| InvoiceLine | 冻结Platform、账户号码、期间、收费；Scheme仅参考当前账户资料，尚未历史冻结 |
| InvoiceSequence / InvoiceIssueAttempt | Company+FC跨日序号；每次尝试保留预留、完成、失败、退回Draft记录，号码不回收 |
| Payment | 不可变现金事实；原`invoice_id`说明首次收款，不表示更正后的当前现金去向 |
| PaymentAllocation | APPLY分配；REVERSAL逐笔引用既有APPLY且只能冲回一次 |
| PaymentRefund / InvoiceAdjustment | 有凭证退款及`COMPANY_BORNE_DIFFERENCE`公司差额，不可更新/删除；差额不是现金 |
| InvoiceCorrection | OPEN→COMPLETED；原/替代关系唯一，完成后不得重写 |
| Attachment / ExportRecord | 文件归属、受控路径、大小/哈希及导出索引；付款/退款凭证认领后冻结 |
| AuditEvent | 关键动作审计；尚未覆盖所有普通资料编辑或提供统一前端时间线 |
| AppSetting | 实际承担Client、Account、StatementImport、BalanceSnapshot的持久ID高水位，防止删除后重用ID；不是闲置预留表 |

原模型依据：[models.py](../backend/app/models.py)。历史`LEGACY_GROUP_HWM`仅保留原组合结果，Invoice兼容汇总行不得伪造账户拆分。

## 3. 逐账户收费、日期边界与HWM

### 3.1 金额和公式

金额以HKD分整数存储，API返回十进制字符串。金额输入最多两位有效小数；会被静默改变的精度输入如`0.004`返回422。费率以bps保存，20%=2000bps；费率百分比最多两位小数。计算使用Decimal/ROUND_HALF_UP；Period Rate以ppm存储。不能用二进制浮点累计财务金额。

令B为Beginning、E为Closing、C为Contribution、W为Withdrawal、H为Original HWM：

| 项目 | 公式 |
|---|---|
| Net Contribution N | C − W |
| Gain/Loss | E − B − N |
| Period Rate | Gain/Loss ÷ (B + N)；分母为0时N/A并禁止Finalize |
| Adjusted HWM | H + N |
| Watermark Difference | E − Adjusted HWM |
| Service Fee | max(Watermark Difference, 0) × Fee Rate，逐账户舍入到分 |
| Next HWM | max(Adjusted HWM, E)，不扣本次Service Fee |
| Days | Closing Date − Starting Date + 1；仅展示，不按天折算收费 |

例如B=1,000、H=1,100、C=100、W=0、E=1,300，损益200、Adjusted HWM=1,200、Service Fee=20、Next HWM=1,300。收费基数受HWM约束，不必等于本期损益。

为保证SQLite精确Period Rate校验，当前重算及相关迁移对Beginning、Net Contribution、Gain/Loss绝对值各限制为HKD 90,000,000,000；超过时明确拒绝，须专门高精度方案。这是技术校验界限，不是业务额度。

每个Sub Account独立计算全部结果；容器汇总已经到分的各账户Service Fee。不得跨账户抵销亏损、共享HWM或先汇总资金再算20%。当前公式版本`HWM-2.0-ACCOUNT`，计算模式`ACCOUNT_HWM`。依据：[calculation.py](../backend/app/services/calculation.py)、[money.py](../backend/app/money.py)。

### 3.2 Snapshot、账户期间与资金下界

- 每个账户的Starting/Closing Date位于所选季度内，并受账户实际管理起止日期约束；中途加入或退出按该账户期间处理，不能套用其他账户的完整季度。
- Closing必须选择该账户的BalanceSnapshot，日期与Closing Date一致，且是季末或实际退出日的合格快照；不能绕过Snapshot手填正式Closing。
- 0.2.30首次Beginning必须选择明确Snapshot，Original HWM仍要求单独填写。**2026-09-12确认的新目标已替代“首次HWM须单独填写、不能根据Beginning默认”的旧要求**：首次HWM自动取客户初始导入、经财务确认的余额快照，落实到各自Sub Account；没有历史HWM资料时同样处理。当前代码尚未实现自动填写，详见[12.2节](#meeting-decisions)。自然季度首日开始时，现有Beginning可选择紧邻上一季末或Starting Date当日Snapshot；非自然季度首日开始时，首次Snapshot须为Starting Date当日。自动HWM不自动放宽这些日期资格，来源不匹配时需明确提示和处理。
- 后续Beginning与Original HWM继承同账户前序Finalized的Closing Snapshot与Next HWM，不能任意更换来源。
- 当前实际资金计算区间为 **`Beginning Snapshot日期 < transaction_date <= Closing Date`**。采用前季末快照时，季度首日流水计入；采用Starting Date当日快照时，当日流水视为已在Beginning内，不再计入。不能统一写成“Starting Date当天永远不算”。

**必须逐季度补齐。** 已有Q1而缺少Q2时，先完成并Finalize Q2，再结算Q3。0.2.21在Calculate/Finalize当前态复验及SQLite Finalize保护中拒绝跳季；Q2只有Draft仍不合格。跨年同样要求连续季度。没有任何历史Finalized账户行的首次结算沿用原首次结算规则，不据此强制补录开户以来所有季度。

计算与凭证复验共同使用`Beginning Snapshot日期 < 资金日期 <= Closing日期`。流水写入/更正/删除锁定保留原Starting至Closing区间，并补充实际使用过的Snapshot后资金日期，防止旧版本跳季产生的历史漏洞；已存在的Finalized结果不回写或自动重算。

来源：[settlement_current.py](../backend/app/services/settlement_current.py)、[季度边界迁移](../backend/alembic/versions/d4f8a1c73b29_quarter_opening_boundary.py)。

## 4. 账单导入、OCR、Sol与人工确认

### 4.1 本地导入及账户匹配

本节所述Company绑定/激活条件属于0.2.30现有流程；公司解绑目标已确认，待按[第12节](#meeting-requirements)同步修改Schema、导入及档案校验，不能只移除表单字段。

支持JPG、PNG、PDF，单文件上限25MB，按真实格式检查。PDF优先读取文字层；本地扫描OCR最多处理前20页，超限保留警告并要求人工核对剩余页面，并非完整识别全部页。Sol对超过20页的PDF直接拒绝并要求拆分。长截图使用重叠切片。当前针对已支持的eMPF/BCT类版式，不承诺任意金融账单都能识别。

本地解析保存文档分类、客户/账户/计划、币种、As-of Date、Total Balance、累计参考字段、基金持仓、置信度、警告和解析器版本。累计净供款、累计投资盈亏属于lifetime参考，不映射为本季度资金或损益。

Windows本地OCR从完整安装包加载。0.2.29按`packaging/tesseract-runtime.json`校验95个EXE、DLL及语言/配置文件；中文安装路径使用数据盘根目录下`FinancialFeeSystem-OCR/<安装路径摘要>`的英文缓存，每次识别核对全部哈希，缺失或损坏文件从已校验安装包原子补齐。可用`FINANCIAL_OCR_CACHE_ROOT`指定有写权限的英文缓存根；本机默认`F:\FinancialFeeSystem-OCR`。缓存仅含可再生OCR组件，不在业务全量数据包内；不再使用旧TEMP共享缓存。当前随包语言为eng及osd，不能据此宣称完整中文或任意版式识别。

启动前校验语言加载；Windows识别进程显式使用已校验目录的TESSDATA_PREFIX，覆盖遗留环境值，避免pytesseract保留配置引号导致找不到语言文件，支持带空格的英文路径。Windows原生子进程故障返回页面警告，避免缺DLL模态弹窗挂住上传。检查限10秒，单次图像OCR调用限30秒；多页/切片文档仍有多次调用。安装包本身缺失或校验失败时停止本地识别，保留导入原件供修复后复核，不自动入账。已有Sol候选及已确认记录仍遵守重新识别限制。实现见[ocr_runtime.py](../backend/app/services/ocr_runtime.py)及[发布OCR检查](../scripts/check-ocr-runtime.py)。

文件SHA-256精确重复返回原记录；账户号、日期、余额等语义重复提示复核。人工明确选户时提交并核对Platform身份；界面展示Client、Platform、Account Number、Scheme及分配的Fee Plan，切换导入记录后重新选户，防止跨Platform同号错挂。

找不到账户时可创建DRAFT Client/SubAccount并保存Snapshot。进入正式结算前，Client须有Company、FC、Management Start Date，Account须有Platform、Fee Plan和开始管理日期等完整归属并激活。补录实际结束日会审计化重核未锁定导入Snapshot的Closing资格；若早于未作废Settlement的Closing，或资格变化涉及已引用Snapshot，拒绝修改。

### 4.2 Sol的当前实现

当前模型精确固定为 **`gpt-5.6-sol`**，低推理档位、严格结构化Schema；请求及回执都必须匹配，不接受前端改模型、静默重路由、第二模型或失败后升级重试链。

应用通过内置Codex App Server的本地stdio协议使用用户本人ChatGPT管理登录，不接受、保存或复制OpenAI API Key。登录与桌面Codex分离。单次识别前检查认证模式、模型、额度及隔离状态；失败保留OCR并交由人工，不妨碍其他财务功能。

专用CODEX_HOME内的`recognition-workspace`作为进程、Thread和Turn工作目录。子进程清理外部CODEX_HOME；固定项目根、`project_doc_max_bytes=0`、空fallback及`instructionSources`检查共同阻止继承源码AGENTS、桌面插件/Hook/MCP。仍出现指令来源时明确失败，不放宽限制。

用户主动点击时，JPG/PNG转换为去EXIF/ICC的临时PNG，PDF逐页渲染后按序在同一Turn发送给OpenAI。最多20页，结束后清理传输图片。每个导入记录最多消费一次识别；并发调用通过锁和幂等检查限制。已确认记录不得重跑OCR或AI；已有AI比对结果后不允许重跑OCR破坏审计基线。

### 4.3 交叉核对与财务写入

按标准化字段和基金名称匹配，输出AGREED、INCOMPLETE或CONFLICT；无论哪种状态，`requires_financial_confirmation`始终为true。AI只能更新StatementImport候选及相关审计，不能创建或修改Snapshot、Transaction、Settlement、Invoice或Payment。

本地`unknown`、Sol有效分类为`empf_account_page`时，允许财务查看原件后**额外确认文档类型**，再完成各字段冲突确认。本地已明确分类为供款或转入等非余额凭证时，不允许Sol覆盖成余额页。关键字段缺失或格式不合法时不得确认。

0.2.30确认页把“客户归属”与“匹配已有账户”分开：新账户通过`client_id`归属明确选择的客户，仅创建子账户草稿；首次出现且无同名客户时才同时创建客户及账户草稿。选择已有账户时联动其客户，改变客户清空账户，改变原件或客户姓名清空两项选择。客户清单失败时不可确认。

后端校验客户姓名（忽略大小写及多余空白）、账户归属、Platform与Scheme；同名客户存在而新账户未指定客户时返回409，绝不单凭姓名自动合并。确属不同人的同名客户须先在客户页明确建立，再选择其档案。已关闭客户不可新增子账户。返回`client_id`、`created_client`及兼容的`created_draft`（表示新建账户），审计记录客户与账户创建情况。

最终confirm保留原件、OCR/AI候选、人工值和持仓，关联账户并生成BalanceSnapshot，记录确认来源和审计。它不会生成Contribution/Withdrawal，不会自动Calculate/Finalize。非季末且非实际退出日的快照仅作普通日余额。

## 5. 结算、开票、收款与更正

### 5.1 Settlement

`DRAFT → FINALIZED → VOID`；VOID后的同自然键Calculate建立下一版本，`v2 replaces v1`、`v3 replaces v2`，不改写旧记录。

Calculate根据当前账户、快照、流水及HWM建立或更新活动Draft。Draft可先缺凭证；Finalize须取得`BEGIN IMMEDIATE`写锁，重新加载当前Client/账户状态、Company/FC、费率、Snapshot、Transaction、前序和公式结果，逐字段比对；陈旧Draft返回409要求重新Calculate，不能在锁外核验后直接提交。

同账户同季度不能通过换Platform/FeePlan重复结算，存在后续非VOID账户结算时不能回头补算。Finalize冻结财务结果和受保护来源，并复验实际资金区间内的实体凭证；0.2.21已修复首日遗漏，原复现条件和回归依据见第11节。

Draft可受控删除并留审计；Finalized只能填写原因Void，VOID历史不删除。存在活动Invoice来源或下游HWM依赖时不能Void，应先处理Invoice并按时间倒序处理依赖。重建版本须完整、连续，不能通过直接SQL改历史。

### 5.2 Invoice来源和签发

**待实施变更（2026-09-12）**：收款公司改为账单出具前选择，不由客户/FC/收费计划公司归属决定；编号拟采用“202609001”样式，但生成规则仍待解决。本节下面的公司一致性及编号算法是0.2.30代码现状，不是新目标，迁移影响和未定口径见[第12节](#meeting-requirements)。

2026-09-10用户确认：**各子账户后台独立计算，最终按同客户、同年度季度合并一张缴费单**。Invoice按Client + 年度 + 季度自动纳入**全部**Finalized Settlement；跨Platform及跨FeePlan合并，Company/FC冻结归属不同则拒绝。费率取各账户所在Settlement已锁定的费率，金额只相加已经舍入到分的账户服务费，不以首个计划重新算费。包含零收费来源和账户行，整体应收必须大于0才建立Invoice。

Draft后出现新Finalized来源，Issue必须拒绝漏项并要求作废重建。Issued后迟到来源必须保留原编号/PDF并更正重开，不另开第二张活动季度单；0.2.27支持合法新增“平台＋收费计划”组合加入完整替代单；同一平台下新增另一计划不是重复来源，见F-03及11.6节。

Issue编号为`收款Company全名-FC名字缩写-IssueDateYYYYMMDD-N`。例如`甲公司-TW-20260907-1`。N按实际收款Company+原FC跨日期延续，不从Client管理月份取日期；Void、失败、碰撞跳号的号码永久保留。Due Date不得早于Issue Date，默认付款天数来自实际收款Company，可在Issue时覆盖。

状态为`DRAFT → ISSUING → ISSUED`，必要时转VOID。先在短事务预留号码/尝试，再在事务外生成双语PDF，归档完成后提交。遗留ISSUING仅在唯一完整双语归档成立时COMPLETE，否则RETURN_TO_DRAFT清理部分文件并保留消耗号码。不能把长时间渲染塞入持久写锁，也不能覆盖已经签发的历史PDF。

`POST /api/invoices`按`client_id/year/quarter/language`创建完整季度单；兼容请求字段`fee_plan_id`已弃用，即使发送也不筛选来源。响应保留兼容锚点`fee_plan_id`，新增`fee_plan_ids`列出来源计划；`fee_plan_name`汇总各来源当前计划名。每个`account_lines`返回来源`fee_plan_id/fee_plan_name/fee_rate_percent`，费率来自冻结Settlement，计划名称和Scheme属于当前资料，不伪称历史名称快照。

候选预览提示该客户本季Active、管理期间重叠且尚未纳入来源的账户，包含缺少计划的账户；这是核对提示，不是“所有账户已结算”的服务端证明。来源完整性的硬性保护覆盖全部已Finalized Settlement，尚未建立/未激活、管理日期未填或Closed账户不会自动补算。财务应先在组合总览核对所有实际受管账户，处理缺资料及遗漏，再开单。

### 5.3 日常收款

付款业务仅UNPAID/PAID；逾期按Issued、未付及Due Date派生`is_overdue`，不是额外付款状态。

一次确认须有正数实际现金、非空付款方式、日期和完整且未认领的PAYMENT凭证，并满足：

`实际现金 + 公司承担差额 = Invoice金额`

公司差额为正时原因必填，为0时不填原因。日常不接受部分付款、第二笔付款或重复确认。现金分配、付款、差额和凭证同一事务认领并冻结；公司差额是结清调整，不是现金收入。

### 5.4 错单、退款和连续更正

有活动现金的原单须从Issued发起Correction。系统建立OPEN，原Invoice转VOID并保留编号/PDF，以等额REVERSAL冲回当前有效APPLY。没有现金且无需错单替代关系时可直接Void；需要保留替代关系的未付原单也可发起Correction。

更正金额或结算来源时，财务依次处理旧Settlement、建立并Finalize替代版本、建立并Issue同组替代Invoice，再完成Correction。来源校验要求每个原“平台＋收费计划”组合沿严格replaces祖先链被唯一替代一次；同一客户年度季度的新平台或新收费计划组合可加入。财务来源更正不能直接复用未更正的原来源（仅更正收款公司的例外见第5.5节），不能漏掉原来源、重复同一平台计划组合、跨客户季度混用或构造循环。接口、前端选择及数据库保护执行同一规则。

完整来源集合在创建和Issue时复验；替代单签发之后又出现迟到来源时，先完成当前Correction，再按正常受控更正处理下一版，不能改动已签发字段。

原单有现金时，替代单必须尚无Payment、Allocation、Adjustment。每笔Payment填写本轮保留额及退款，满足：

- `本轮保留APPLY + 本轮退款 = 本轮REVERSAL`。
- `替代单保留现金合计 + 本轮公司差额 = 替代Invoice金额`。
- 连续更正全链：`Payment原始现金 = 当前净分配 + 累计退款`。

退款须逐笔记录日期、方式、原因及未认领的PAYMENT_REFUND实体凭证。下一轮只处置上一轮仍活动的现金，不能重复使用已退款金额。OPEN占用的替代Invoice不能先收新Payment或再次发起Correction，必须先完成本轮。没有原Payment时，完成更正只建立替代关系，新单保持UNPAID，不虚构现金或公司差额。

| 已确认情形 | 正确记录 |
|---|---|
| 原收120，正确应收100 | 保留分配100，退款20并关联凭证；不再登记一笔100现金 |
| **2026-09-07确认：原收100，计算失误后正确应收120** | **保留100现金，公司承担20并记录计算失误原因，客户不补款**；现有`company_difference`与结清校验可表达该情形 |
| 客户少付且公司决定承担小额差额 | 实际现金加获确认公司差额结清；金额巨大由用户另行决定，不推导无限额自动减免 |

## 6. 凭证、删除条件和审计

### 6.1 证据保护

Beginning、Closing、Contribution、Withdrawal和Payment均需原始凭证及人工确认。Snapshot可通过StatementImport原件或SNAPSHOT附件证明，Transaction使用TRANSACTION附件。Payment/Refund先上传未认领附件，再由记账事务认领。

实体校验包含受控数据根、普通非空文件、登记大小和SHA-256；付款/退款还检查凭证业务归属与占用。哈希用于证明文件完整性，不因两份凭证内容相同就自动判定为同一现金业务。应用复验实体文件，外键/Trigger保护数据库关系，二者不能互相替代。

未锁定流水可PATCH日期、CONTRIBUTION/WITHDRAWAL类型、金额和备注，强制2至500字符原因；保留Transaction ID和原凭证，`TRANSACTION_CORRECTED`记录before/after/reason。无实际变化返回400，旧日期或目标日期命中Finalized保护返回409；Draft不会自动更新，须重新Calculate。0.2.21同时保护旧版本跳季期间实际使用的流水，见F-02。

### 6.2 删除和撤销边界

| 对象 | 放行条件和结果 |
|---|---|
| Company/FC/Platform/FeePlan | 无下级资料、Settlement、Invoice（含收款主体）、Correction目标、序号及相应审计/附件/导出历史引用才可删；不级联清理业务 |
| Client/SubAccount | 没有下级账户、流水、Snapshot、确认导入、Settlement及附件/导出等受保护引用；写锁、Core SQL和Trigger共同避免ORM级联；保留最小审计 |
| 未确认StatementImport | 无异常确认痕迹、Snapshot关系、重复后继或原件共用；现存原件校验后删除记录/文件/识别结果；原件已缺失时明确说明，不冒称完整 |
| 已确认误入账StatementImport | 2至500字符原因及二次确认；与唯一Snapshot双向来源一致；无任何状态Settlement账户行、附件、导出或duplicate_of后继引用；原件存在且哈希有效。仅撤销该Snapshot/持仓及导入/原件/识别结果，保留原ID、原因、摘要、哈希审计及Client/Account |
| Settlement | 仅Draft可删除；Finalized经Void保留历史；VOID对Snapshot的引用同样阻止误入账撤销 |
| 手工Snapshot、普通附件、流水删除/冲正 | 尚无完整更正/删除能力，不能把修改数据库当作正常操作 |

导入上传/OCR、reparse、Sol、confirm和delete共享锁。删除先校验现存原件并在同目录原子暂存，提交失败恢复，成功清理；`.delete-pending`只由启动恢复器按数据库引用及审计证明收敛。上传提交不确定使用`.upload-pending`标记；原件在OCR前后校验。证据不明确则停止，不猜测孤儿归属或手工删标记。

### 6.3 审计和维护原则

Finalize、Void、Issue、Payment、Correction、导入确认/删除、AI识别及流水受控更正等关键动作已有审计。普通资料修改审计不全面，前端也没有统一AuditEvent时间线。

保留客户财务ID、历史归属、编号、PDF和现金事实；纠错用原因及新版本/新台账表达。不能为“简化”去掉写锁、精确凭证、恢复journal或数据库契约，也不为未证实问题堆叠静默fallback。具体修复先证明路径和根因。

### 6.4 未结算重复客户整理

用户于2026-09-11确认：同一人的两个子账户应归在一个客户档案下，各子账户保留自己的收费计划；不能因导入新账户而创建第二个同名客户。

### 8.2 关闭页面与程序生命周期

2026-09-08用户明确取消网页“安全退出系统”按钮，要求直接关闭浏览器窗口即退出系统。0.2.24移除该按钮、退出完成屏及旧的轮询逻辑；原逻辑在6秒超时后仍显示退出成功的误导提示一并移除。

- 每个系统页面通过`WS /api/browser-session`保持独立连接；最后一条连接断开后等待3秒，再调用既有ShutdownCoordinator停止本应用拥有的Sol子进程并让Uvicorn正常排空在途请求、退出。连接注册只存进程内存，不新增数据库表、登录状态或财务写入。
- 刷新、页面返回或3秒内重新打开会取消待退出任务；关闭多个系统页面中的一个不会影响其他页面。最小化、切换标签不退出。浏览器正常关闭及进程结束由连接断开触发，不依赖不可靠的卸载HTTP请求或后台定时心跳。尚未有网页连接的服务保持启动，供首次加载及隔离HTTP验收。
- WebSocket只允许loopback客户端和本系统页面Origin；开发5173代理显式启用WebSocket转发。外站、缺失Origin及错误端口不能注册页面或触发关机。
- 重新双击程序时，启动器核对已有服务的应用名称、版本、loopback及数据根；匹配则打开已有页面，不再启动第二个服务。不匹配则明确报端口由其他程序、不同版本或不同数据目录占用；不能借重开切换财务数据。
- `POST /api/shutdown`仍供受保护的恢复与运维流程使用，原本机来源及写标记校验不变。用户界面不再提供独立退出按钮。已提交请求按正常服务关闭流程完成；未提交表单不自动保存。

实现依据：[页面连接](../frontend/src/useBrowserSession.ts)、[连接路由](../backend/app/routes/browser_sessions.py)、[生命周期](../backend/app/services/browser_sessions.py)、[启动器](../backend/app/launcher.py)。浏览器事件边界依据[MDN pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event)；不能将visibilitychange中的切后台当作关闭窗口。

### 8.3 API地图

OpenAPI为`GET /api/openapi.json`，交互文档为`/api/docs`。所有`/api/*`非GET/HEAD/OPTIONS请求带`X-Financial-System-Request: 1`，前端`api.ts`统一注入；这不是多用户认证机制。

TrustedHost限制loopback Host，测试模式才增加testserver；开发CORS只允许127.0.0.1/localhost的5173来源且不带凭据。导入恢复与普通财务写入通过全局门闩互斥。SPA入口返回`no-store`避免旧页面加载旧资源；未知`/api/`路径返回404，不回落为前端HTML。

### 8.5 前端设计与交互契约

按`ui-ux-pro-max`开展全站审查。技能库自动匹配的企业官网/全黑主题不适用于本机财务工作台，最终采用人工核对后的深海军蓝导航、暖白内容区和金色金额重点；使用本机字体及Lucide图标，不新增在线字体、外部服务或依赖。

- **样式职责**：`frontend/src/styles.css`维护颜色、字号、间距、基础控件及断点；`styles/workflows.css`保留可读的业务专用布局。正文/输入以14–16px为主，表格及辅助信息12–14px，外围英文标记10–11px。禁用、焦点、错误及状态同时有文字语义；减少动态效果偏好会关闭非必要动画。
- **工作台导航**：八个页面分为工作台、日常财务、管理；`#/clients`等地址支持刷新保留页面和浏览器前进/后退。未带功能地址且没有Company时才引导首次设置，慢请求不覆盖用户导航。页面按需加载，页面加载或渲染异常提供刷新入口并保留外层导航。小窗口抽屉限制焦点，Escape关闭并归还焦点。
- **页面分区**：客户、资金及Invoice清单放在新增表单之前；长页面顶部“本页”按钮只滚动/聚焦目标，不切换功能、不销毁表单。选择历史Settlement或Invoice后定位结果/详情。功能切换、刷新或关闭页面仍不自动保存未提交内容。
- **客户与账户搜索**：共用`SearchableSelect.tsx`采用单一可搜索选择框。按中英文名称片段匹配，忽略英文大小写及全角/半角；已有账户匹配支持完整账户身份。搜索不会更改已选ID；Escape、无结果或失焦保留原选择，必须点击候选或用方向键加Enter明确确认，单独Enter不会提交业务表单。必须选择列表项，单纯输入姓名不能代替有效ID。候选超过100项时只渲染前100项并提示继续输入关键词，匹配始终覆盖完整本地列表。
- **筛选与分页**：客户清单可搜姓名/Company/FC及状态，每页10位；Invoice可搜客户/编号和付款/生命周期/逾期状态，每页20张；导入记录可搜文件名及复核状态，每页12条。改变筛选回到第一页，清空恢复全部。分页只改变清单，不清空创建表单或当前选择。基础资料支持按名称/Code搜索。分页均在当前已加载数据内进行，未增加服务端分页。
- **财务操作**：季度结算按客户实际本季Active账户联动平台和Fee Plan；切换客户清空平台和计划，切换平台清空计划，切换年度季度重新选择。本季组合总览每页10组显示账户及已锁定覆盖数，可建立或查看指定组合。历史结算可搜索客户/平台/计划/账户/季度并按状态筛选，每页20条；结果明确显示自身客户、平台、计划、冻结费率和季度，避免和未提交输入混淆。选齐Client、Platform、Fee Plan才显示同组账户，行内日期/Snapshot/HWM控件有完整账户标签。客户切换公司、账户切换客户时重置依赖FC或计划选项。待确认档案激活、建立Invoice Draft复用`useFormAction`的在途保护和已保存/刷新失败区分。API前置规则、金额与来源计算仍由原服务端决定。
- **反馈及可访问性**：错误提示保留服务端完整原因并获得焦点；普通操作提示使用中性信息标识、可手动关闭，8秒后自动消失。表格提供可聚焦滚动容器及固定表头，完整金额和长编号不得以省略号隐藏。系统页日常状态优先，数据库/模板具体路径收纳在可展开技术信息中；导入整包的覆盖确认仍完整保留。
- **原件预览**：按服务端`mime_type`区分图片和PDF；保留沙箱PDF预览，并提供“打开原件”链接，浏览器未显示内嵌PDF时可直接查看文件。此入口不代表已运行OCR或Sol识别。
- **生命周期**：`useBrowserSession`仍在App根部只挂载一次；哈希导航和页面按需加载不增加/关闭连接。最后页面关闭、刷新、多标签及可信Origin契约仍见8.2节。不重新增加退出按钮。

主要文件：`App.tsx`、`PageBoundary.tsx`、`components.tsx`、`SearchableSelect.tsx`、`hooks.ts`及八个页面。前端测试覆盖搜索身份、键盘选择/组合输入、必选校验、长列表、分页保留输入、导航/慢请求、页面故障、明确错误反馈、依赖选择及重复请求保护。测试和实际浏览器证据分别登记于11.4节。

## 9. 数据包、换机、迁移与恢复

### 9.1 数据边界

```text
<数据根>/
  database/financial_system.sqlite3
  statement_imports/
  attachments/
  output/excel/ 和 output/pdf/
  backups/
  tmp/（包括ai-codex等受控临时文件）
```

源码仅含脱敏代码、测试、模板及文档；运行包保留整个onedir；业务数据通过完整数据包单独交接。AI独立登录目录不属于业务备份，不复制认证文件到新电脑。新电脑完整解压同版本运行包、选择本地独立数据目录、本人重新登录系统专用ChatGPT账号。不能直接复制运行中的SQLite文件，也不能把开发data连接到正式数据。

### 9.2 季度完整数据包

年度季度仅标记复核批次，不筛选资料。包包含导出时全部数据库记录、账单原件、附件、付款/退款凭证和系统生成文件；复核副本不承担汇总，导入**全量覆盖接收方，不追加、不去重、不双向合并**。

采用SQLite Backup API取得一致副本。创建和恢复均检查数据库完整性、外键、目标Schema/Trigger契约、Manifest及实体文件；数据库和业务目录中的symlink/junction拒绝。唯一临时ZIP自验通过后在同目录原子公布，不能暴露半成品或覆盖并发请求。

新Manifest格式为`financial-fee-system-data-package`、version 1，含精确应用版本、`snapshot_period {year, quarter}`、ISO时间、唯一JSON键、受控成员路径及小写SHA-256。接收方须与发送方精确同版本，新包数据库须为当前head。归档与Manifest普通文件集合精确一致，只有一份指定名称数据库。

StatementImport原件集合与数据库引用集合精确相等；付款/退款、全部Attachment、ExportRecord、Invoice双语PDF逐项校验归属、路径、大小/哈希及内容。缺件、篡改、孤儿原件、pending文件、越界路径及复制期间发生的不一致都拒绝。

旧`financial-fee-system-backup`版本1仍按对应历史Schema契约校验，但没有新包的跨路径保证；不能用它绕过新数据包同版本要求。日常季度交接应由相同版本双方重新导出新包。

### 9.3 导入事务及异常恢复

导入先取非阻塞进程锁，并发请求返回409；全局写入门闩还拒绝在已有财务写入时开始恢复，并在恢复校验期间暂停新写入。校验成功产生`pending_restore.json`后继续拒绝财务写入，保留内部受保护退出接口。真正替换在下一次启动、数据库初始化前进行。

在数据根同卷安全tmp预制database、attachments、statement_imports及output。跨数据根时只在暂存数据库内重定向四类路径：StatementImport、Attachment、ExportRecord、Invoice PDF；受影响Trigger按精确名称和原SQL在同一SQLite事务内撤下/恢复。重定向后重新校验数据库及文件，不能改变原包数据库后继续拿原哈希作比较而冒称相同。

持久化journal记录`preparing/applying/rolling_back/committed`并控制同卷替换。提交前失败逆序回滚；断电后先恢复一致状态再对外服务；committed后只收尾，不回滚。marker、pending和旧目录按证明及安全前缀幂等清理，新marker不被旧事务误删。异常恢复失败须停止并检查，不能人工删除恢复证据强行启动。

正式数据导入需用户明确授权和可验证的现状备份。仅收到开发任务不构成覆盖正式数据的授权。依据：[backup.py](../backend/app/services/backup.py)。

- SQLite的TEXT affinity允许现有Company全名编号；若未来换数据库，须重新评估Invoice及IssueAttempt的长度限制。

**持仓确认遗漏已修复（0.2.28）**：原先本地为空、Sol非空时，统一差异勾选后仍可保存空列表。现在`ImportsPage.tsx`显示实际采用来源及数量；若保存数量少于任一候选，确认按钮暂停，财务应主动选择完整来源。若较少明细才符合原件，必须填写2至500字`holdings_difference_reason`，后端在创建客户/账户/快照前独立拦截遗漏；省略`holdings`、提交null/空数组或部分明细均不能靠统一勾选绕过。原因保存在人工复核值、revision log及STATEMENT_CONFIRMED审计中；来源切换、文件切换及重新识别会清空原因，不能沿用上一项确认。Sol不会被自动采用。数量校验不能证明同数量内容正确，原件逐项复核仍必要。

2026-09-10用户再次确认“是每个子账户”。系统当前收费单位为独立登记的`SubAccount`：各自分配计划、保存余额和流水、继承HWM，最后汇总各账户服务费。`holdings_json`是账户内部基金持仓，识别基金行不自动建立收费子账户；同一会员账号下基金的跨期换仓也不自动继承其他基金HWM。当前确认接口一次关联一个SubAccount，计算不要求两期基金名称/行数相同。合法无持仓明细的余额资料仍能按子账户计算，不把所有空持仓一律视为金额错误。

**保留限制**：本地`statement_parser.py::_extract_holdings`主要支持Manulife/BCT，BOC-Prudential持仓可能漏识别，本轮没有扩大OCR识别承诺。历史已保存空明细且存在非空候选、没有单独原因的导入记录现在显示明确警示；没有自动改写历史Snapshot、Finalized或Invoice，也没有新增历史持仓补正接口。既有结算仍以账户余额/流水为金额依据；提示不等于已冻结或已更正旧账。未被任何Settlement使用的误入账可按正常撤销流程处理；已引用的记录需另行核定受控补正方案。若业务子账户并非系统已登记身份，应先核对、登记，不能把识别出的基金数量当作系统完整账户数。

### 12.2 已确认的业务裁决

**C-01 收款公司与服务关系分开（原13，用户明确回复）。** 客户在**出具账单前**选择本单付款给哪家公司。Company只是收款载体；客户、FC和Fee Plan不再预先绑定Company。不是付款完成后再选公司，也不是只把现有客户Company下拉框搬到另一页。客户的FC服务关系、账户的计划分配仍各有用途，不因取消公司绑定而取消。既有已签发记录、编号、公司资料归档和现金记录保持历史事实，不能按新归属批量覆盖。

当前差距：FC/FeePlan有必填company_id及公司内Code唯一约束；Client激活、账户分配、导入、重复客户整理、Settlement校验、Invoice完整来源和统计/导出均依赖公司。迁移需先列明全局Code重名、历史冻结归属、旧新Invoice兼容及Trigger调整方案；不得自动合并同名FC/计划或删除历史公司资料。新的收款公司必须参与本单公司信息、银行/支票信息、默认付款期限及后续公司筛选。编号如何使用公司仍受Q-01未定规则约束。

**C-02 首次与后续HWM（原3，用户逐项确认）。** 首次HWM自动使用客户初始导入、经财务确认的余额快照，必须分别落实到各自Sub Account；后续继承上次已确认结算的Next HWM。客户存在历史HWM但资料没有提供时，也按该初始余额快照确定初始HWM。不能再以旧文档“首次必须手输、不得直接等于Beginning”否决这一新政策。当前后续继承已有实现，首次自动填写尚未实现。

自动填写应能追溯到具体账户、Snapshot日期/ID和已确认金额，不能用客户汇总余额、基金持仓金额或OCR候选直接代替；不能每导入一张快照就重置HWM。多个可能的初始来源、迟到补录或与开始日期冲突时，不擅自按最小ID/最新上传取值，需明确来源。是否允许财务覆盖以及如何留痕仍见Q-06。既有Finalized历史不得因新默认值重算。

**C-03 计算与账单状态（原7—9，用户明确回复）。** 真正出具客户缴费单后才显示“账单已生成”；之前显示**“收费已计算”**，以此更新原9的“已计算”用词。另一个目标状态为“账单已作废”。0.2.30的FINALIZED只是锁定计算，不能在全局StatusBadge中直接改成“账单已生成”。须结合实际关联Invoice及替代链判断；签发中、失败、尚未开票、仅计算作废等边界见Q-04。日常付款仍是已付款/未付款两个独立状态，不能与计算或作废状态混为一列。

**C-04 Excel修复范围（原5，用户补充）。** 用户指出现有30%与20%利润收费同时导出时表格会出错，要求“系统数据和表格数据要严格对应起来”。目标是现有多计划导出的正确性，不据此新增固定费用、阶梯收费或Defer。逐行核对客户、账户、计划、冻结费率、期间、余额、HWM、费用及相应账单信息，不能只核对总金额。部分复现及证据见12.6节；用户报告的问题不能因为一个样例金额正确就关闭。

**C-05 季度筛选位置（原4，用户补充）。** 用户具体指“本季账户组合总览”：当前主要以客户为主体，希望增加以**年份、季度为主要筛选入口**。不是仅把“建立此账户组合”按钮换字，也不是推定自动选择当前季度或直接跳至下个可结算季度。现有账户管理日期、快照资格和连续季度保护仍适用；选定期间后，账户列表仍按C-07先搜索客户再展示。

**C-06 编号（原1，用户明确暂缓）。** 保留“202609001”作为用户给定的样式例子，单独显示出具日期；用户要求将编号含义、流水范围及重置规则**保留为待解决问题**。不得默认全系统/月度/公司内流水，也不得先实现“看起来像”这一编号的算法。

**C-07 全站账户展示（原12，再次明确确认）。** 全站账户列表先隐藏，搜索并选定客户后才显示该客户的子账户。不仅是客户与账户查询页，其他页面同样执行；不能把输入搜索词但未选择客户当成已选定。此规则控制账户列表展示，不授权删除账户或限制已归档账单文件的读取。

**C-08 概览筛选（原19、20，用户明确回复）。** “数据同步时间筛选”就是经营概览已有的统计年度、统计季度，不是新增导入时间或快照日期筛选。保留右侧年度/季度选择，只删除左侧重复的“2026年度全年”文字。在管客户必须随年度/季度同步变化，不能仅让收费金额变化。用户进一步确认：按所选期间内是否实际受管统计，**即使没有产生服务费或尚未出账单也计入，期间中途加入或退出的客户也计入**。按客户去重，一个客户有多个子账户仍只计一位；不能以期间收费客户数、有快照客户数或当前ACTIVE客户数代替。此口径已确认，0.2.30仍是当前ACTIVE客户总数，尚未实现期间统计。接手时需核对实际管理期间的数据来源及历史可用性，不能用缺失的日期猜测历史归属。

**C-09 账单筛选维度（原11，用户明确回复）。** “收费方式”明确指**收费计划**（如20%/30%利润计划），不是银行转账/支票等付款方式。界面使用明确标签；混合计划同单筛选的整单展示问题见Q-08。
