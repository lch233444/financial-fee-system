## 1. 一页接手摘要

### 1.1 项目是什么

这是一个Windows本地运行的金融计划收费管理系统，用于把依赖Excel的季度收费流程转成可审计的工作流：

```text
基础资料
  → eMPF账单导入与人工复核
  → 账户余额和资金流水
  → 季度High Water Mark结算
  → Invoice签发
  → Payment登记
  → FC统计、Excel/PDF导出
  → 完整备份与恢复
```

系统的第一原则是财务准确与人工最终确认，不是追求无人值守。OCR和Luna都只能产生待复核候选值，不能直接写入正式财务链路。

| 前端 | React 19、TypeScript 5.9、Vite 7 |

## 2. 业务边界与非目标

### 2.1 当前用户与运行边界

- 当前MVP面向单台Windows电脑上的财务人员。
- 操作界面为中文，保留Beginning、Closing、HWM、Service Fee、Invoice、Payment等常用英文财务术语。
- 后端只能监听 `127.0.0.1`、`localhost` 或 `::1`。
- 当前没有用户登录、角色权限、多人并发或公司服务器部署。
- 业务数据由用户选择本机数据根，与源码、运行包和Git仓库分离。

### 2.2 已实现范围

- Company、FC、Platform、Fee Plan、Client、Sub Account基础资料。
- Contribution/Withdrawal、Balance Snapshot与账户附件。
- eMPF账单分类、本地OCR、Luna辅助识别、交叉核验、人工确认与审计留痕。
- 多账户组合的季度HWM计算、Draft/Finalize/Void与HWM继承。
- Invoice Draft/Issue/Void、连续编号、中英文归档PDF、多笔Payment。
- Dashboard、FC统计、内部Excel、客户结算PDF、完整备份与延迟恢复。
- Windows一键运行包、首次数据目录选择、页面安全退出。

### 2.3 未实现或不能声称已完成

- Defer延付利息计算。
- 自动邮件发送、用户权限、多人协作、服务器/局域网部署。
- 任意版式OCR、网页自动抓取、历史批量导入、模板版本管理。
- 定时备份、备份加密、完整数据保留与删除政策。
- Payment退款/冲销、Credit Note、错误付款撤销。
- 完整前端审计日志和浏览器E2E测试。

### 2.4 已确认业务背景与目标口径（2026-08-27）

本节记录用户已经明确确认、但不一定已经由0.2.3代码实现的业务事实。后续对话或实现不得仅因当前Schema/API不同而推翻本节；规则变化必须再次获得用户明确确认并当次更新本文和CHANGELOG。

#### 角色、收款与当前范围

- Company是向客户出具Invoice并实际收款的主体。
- FC是介绍客户并持续为客户提供服务的中介人/归属人，不是公司收款人员；不得把公司收到的Payment描述为“FC收款”或“FC收款业绩”。
- FC统计只展示“当前管理客户数”“本季度产生收费的客户数”和这些客户产生的Service Fee，不展示已收、未收、Payment或任何FC收款指标。
- 当前真实业务只有工作簿`利润20%`所代表的一种收费计划，费率为利润的20%。现有FeePlan可配置能力只是技术扩展性，不代表用户已经采用其他收费计划，也不得据此反复询问当前多Fee Plan合并规则。
- `Defer 延付利息（待确认）`暂不考虑、不得接入计算或列入近期计划。
- 0.2.3仍在开发；下一阶段目标是先把Windows单机版做稳并投入实际使用，不开展服务器、多用户或权限架构。

#### Sub Account计算与客户Invoice

- 每个Sub Account完整、独立地计算Beginning、Closing、Contribution、Withdrawal、Original/Adjusted/Next HWM和Service Fee；每个Sub Account拥有自己的HWM链。
- 不同Sub Account之间不得抵销盈亏或共用HWM。即使属于同一Client、同一Fee Plan或不同Platform，也必须先逐账户计算Service Fee，再把各账户Service Fee相加。
- 不同Platform、同一20%收费计划的多个Sub Account可以在最终给客户的同一张季度Invoice中合并。这里的“合并”只发生在出具客户账单阶段，不是把账户资金、损益或HWM合并计算。
- 合并Invoice应逐行列出每个Sub Account的Platform、账户号码和Service Fee，并在底部汇总客户应付总额。
- 当前只有一个收费计划；未来若出现不同Fee Plan，是否同单出具必须重新向用户确认，不能自行从通用数据模型推导。

#### 快照、凭证与正式状态

- Closing必须来自属于对应Sub Account、日期及金额一致且符合季末/实际退出日资格的Balance Snapshot；不得在正式结算中跳过`closing_snapshot_id`手填Closing。
- Beginning应自动关联同一Sub Account上一季度已锁定Closing；首次结算或无法继承时，必须关联一份明确、人工确认的期初Balance Snapshot。
- Contribution、Withdrawal、Beginning、Closing和Payment均需要原始凭证及人工确认。
- 允许先保存缺少凭证的Draft，方便逐步录入；但缺少凭证的Contribution/Withdrawal不得纳入正式结算，Beginning/Closing缺少凭证不得Finalize，Payment缺少凭证不得把Invoice标记为已付款。

#### Payment和账单纠错

- 日常Payment只保留`UNPAID`和`PAID`两种业务状态，不提供部分付款流程，也不把逾期或部分付款建模为额外付款状态。
- 客户因错误Invoice多付时，必须保留原Invoice、编号和归档PDF的审计记录，将其标记为已更正/作废，重新出具正确Invoice并记录退款及退款凭证；不得覆盖原文件。
- 客户少付且公司决定承担小额差额时，记录实际Payment和公司承担差额，两者合计结清Invoice并标记`PAID`。金额巨大时不自动处理，由用户另行决定。
- 一般原则是发给客户的Invoice必须在Issue前经过严格复核，尽量避免事后更正。

### 3.4 后端分层约定

- `routes/`：接收输入、加载关联对象、检查状态、控制数据库事务并记录审计。
- `services/`：放可复用的纯计算或外部集成，不应绕过路由层的财务状态检查。
- `models.py`：承担唯一键、外键和持久化约束，但不是所有业务规则的唯一位置。
- `schemas.py`：承担格式、范围和枚举校验；任何新增写接口必须复用或新增显式Schema。
- `serializers.py`：统一对外金额字符串和派生状态，避免前后端各自发明口径。

## 4. 领域模型与数据关系

### 4.1 核心关系

以下关系图描述0.2.3当前实现，不等于2.4节确认的目标结算模型：

```text
Company ─┬─< FC
         ├─< FeePlan
         └─< Client >─ FC
                 └─< SubAccount >─ Platform / FeePlan
                       ├─< TransactionRecord
                       └─< BalanceSnapshot

Client + Platform + FeePlan + Year + Quarter
                 └─ QuarterlySettlement
                      ├─< SettlementAccountLine >─ SubAccount
                      └─ Invoice ─< Payment

StatementImport ──人工确认──> BalanceSnapshot
Attachment / ExportRecord / AuditEvent 为横向证据与审计记录
```

目标模型应演进为：

```text
SubAccount + Year + Quarter
        └─ 独立Settlement/HWM/Service Fee

Client + Year + Quarter + 当前20%收费计划
        └─ 客户Invoice
             └─ 多个SubAccount收费明细（可跨Platform）
```

### 4.2 实体职责与关键约束

| 实体 | 职责 | 关键约束/自然键 |
|---|---|---|
| Company | 公司收款、支票资料和付款天数 | `name`、`code`唯一 |
| FC | Company内的客户介绍与服务归属中介人；不是收款人 | `(company_id, code)`唯一 |
| Platform | 计划平台/受托人 | `name`、`code`唯一 |
| FeePlan | Company内收费计划与费率 | `(company_id, code)`唯一；费率以bps保存 |
| Client | 客户及归属Company/FC | ACTIVE前必须有Company、FC、Management Start Date |
| SubAccount | 客户的平台账户 | `(platform_id, account_number)`唯一；ACTIVE前必须有Platform、Fee Plan |
| TransactionRecord | 账户级Contribution/Withdrawal | 金额必须大于0；日期参与季度区间汇总 |
| BalanceSnapshot | 某账户某日余额与持仓 | `(account_id, as_of_date)`唯一；Closing资格单独保存 |
| StatementImport | 原件、OCR、Luna、人工值和修订轨迹 | 文件SHA-256唯一；CONFIRMED后不可重新OCR/Luna |
| QuarterlySettlement | 0.2.3当前为组合级季度结算和HWM；冻结Company/FC及前序结算 | 当前`(client, platform, fee_plan, year, quarter)`唯一；目标改为Sub Account独立HWM |
| SettlementAccountLine | 结算内账户级Beginning/Closing | `(settlement_id, account_id)`唯一 |
| InvoiceSequence | Company+FC连续号码 | `(company_id, fc_id)`唯一；Void号码不回收 |
| Invoice | 正式收费单及归档PDF | 当前一个Settlement只能有一个有效Invoice；目标为客户季度Invoice汇总多个账户收费明细 |
| Payment | Company实际收到的Invoice款项 | 当前支持多笔且累计不超额；目标只保留未付/已付并支持公司差额与退款留痕 |
| Attachment | 账户等实体的原始凭证 | 保存原名、存储路径、MIME、大小和SHA-256 |
| ExportRecord | Excel/PDF导出索引 | 保存文件路径、类型、语言和SHA-256 |
| AuditEvent | 关键状态变化审计 | 目前覆盖确认、Finalize、Void、Issue、Payment、AI识别等关键动作 |
| AppSetting | 预留的键值配置 | 当前不是主要用户配置来源 |

### 4.3 金额和费率类型

- 所有正式金额以HKD“分”的整数写入数据库，例如 `1234.56` 保存为 `123456`。
- API金额输入最多两位有效小数；任何会在转成整数分时静默改值的输入（例如`0.004`）直接返回422，不进行隐式舍入。
- Fee Plan费率百分比最多两位小数，并精确转换为basis points；20%为2000 bps，禁止使用`int()`静默截断。
- 写接口返回数据库持久化后的金额或费率口径，不回显可能与落库值不同的原始输入。
- Period Rate以parts per million保存，API序列化时除以1,000,000。
- 禁止在新增代码中用二进制浮点直接累计财务金额。

## 5. 业务工作流和状态机

### 5.1 基础资料

1. 建立Company。
2. 在Company下建立FC和Fee Plan。
3. 建立Platform。
4. 建立Client并关联Company、FC。
5. 建立Sub Account并关联Client、Platform、Fee Plan。

Client和Sub Account都可先以DRAFT保存不完整资料。“客户与账户”页面提供专门的Draft补全表单：先补齐并激活Client，再补齐Platform/Fee Plan并激活Sub Account。转为ACTIVE时后端再次校验必填关联，且Sub Account的Client也必须已经ACTIVE；前端提示不能代替后端保护。当前PATCH接口允许在三个状态值之间更新，尚未强制单向迁移，因此调用方不能假设状态只能前进。

```text
Client/SubAccount状态值: DRAFT / ACTIVE / CLOSED
```

### 5.2 账单导入

```text
上传原件
  → magic bytes/25MB/哈希检查
  → 本地OCR与文档分类
  → NEEDS_REVIEW
  ├─ 可选：Luna单次辅助识别与交叉核验
  └─ 财务人工确认
       → CONFIRMED
       → 建立BalanceSnapshot
```

- 精确哈希重复直接返回原记录。
- 账户号+日期+余额相同属于语义疑似重复，保留记录但提示人工核对。
- 只有 `empf_account_page` 可以确认成Balance Snapshot。
- `contribution_record`、`contribution_asset_transfer_record` 和 `unknown` 在服务端硬性禁止入账。
- 若没有匹配账户，确认流程可以建立DRAFT Client/Sub Account；它们仍需补全资料才能ACTIVE。
- 导入确认产生的季末/实际结束日快照会成为Closing候选；手工快照还必须由用户勾选Closing资格，季末日期不会覆盖用户的取消选择。

### 5.3 Settlement

```text
calculate → DRAFT → finalize → FINALIZED
              │                    │
              └──── void ──────────┴→ VOID
```

- 结算唯一边界是 `Client + Platform + Fee Plan + 年度 + 季度`。
- 同一结算中的所有Sub Account必须属于该组合。
- DRAFT可以重复calculate并替换账户明细。
- FINALIZED或VOID不能原地重算。
- Calculate持久化最近一期FINALIZED Settlement的ID作为`previous_settlement_id`；存在后续非VOID结算时禁止补建或重算更早期间。
- Finalize会重新核对前序ID及Next HWM，并冻结当时的Company/FC；存在后续结算时禁止倒序Finalize。
- Finalized期间覆盖的账户不允许补录Contribution/Withdrawal；路由预检查与SQLite Trigger双重保护，避免并发请求让账本与锁定结算分叉。
- Settlement存在Draft、Issuing或Issued Invoice时不能Void；必须先处理关联Invoice。
- Void必须按时间倒序进行；存在下游非VOID Settlement时拒绝作废，重复Void也返回409。
- Finalize写入时间并记录AuditEvent；公式版本、计算快照、历史归属及HWM来源随后视为不可变。

以上是0.2.3当前实现。目标规则已由用户改为“每个Sub Account独立Settlement/HWM”，因此现有`Client + Platform + Fee Plan`组合级HWM只能视为待迁移实现，不能继续作为不可变业务决定。

### 5.4 Invoice和Payment

```text
Invoice生命周期: DRAFT → ISSUING → ISSUED → VOID
                    └──────────────────→ VOID
付款派生状态:    UNPAID / PARTIALLY_PAID / PAID / OVERDUE
```

- 只有FINALIZED且Service Fee大于0的Settlement可生成Invoice Draft。
- Invoice使用Settlement Finalize时冻结的Company/FC，不受Client以后改归属影响。
- 编号在短事务中分配：`CompanyCode-FCCode-ClientStartYYYYMM-NNN`。
- `NNN`按Company+FC持续递增，不按月份重置，Void后不复用。
- Issue先在串行短事务中预留编号并进入内部`ISSUING`状态，再在数据库写事务外生成中文和英文临时PDF；双文件成功后以短事务写哈希并转为ISSUED。渲染失败会恢复Draft但不复用已消耗号码。
- PDF、Excel和结算PDF的生成/补档接口均使用受写请求标记保护的POST；GET只用于真正只读资源。
- 有Payment的Invoice目前禁止直接Void。
- 部分付款优先显示 `PARTIALLY_PAID`；现实现不会额外叠加OVERDUE标签。

以上付款状态和“一条Settlement对应一张Invoice”是0.2.3当前实现。目标是跨Platform汇总多个独立Sub Account收费明细到客户季度Invoice，并仅保留`UNPAID/PAID`业务状态；具体差距见2.4节和17节。

## 6. HWM计算规则

### 6.1 公式

```text
Net Contribution      = Contribution - Withdrawal
Gain/Loss             = Closing - Beginning - Net Contribution
Period Rate           = Gain/Loss / (Beginning + Net Contribution)
Adjusted HWM          = Original HWM + Net Contribution
Watermark Difference  = Closing - Adjusted HWM
Chargeable Above HWM  = MAX(Watermark Difference, 0)
Service Fee           = Chargeable Above HWM × Fee Rate
Next HWM              = MAX(Adjusted HWM, Closing)
Days                  = Closing Date - Starting Date + 1
```

### 6.2 不变量

- Days仅展示，不参与收费。
- Starting Date当天资金视为已包含在Beginning；流水区间为 `transaction_date > start_date && <= closing_date`。
- 首次Original HWM必须由财务输入，系统不能猜测为Beginning或管理起始金额。
- 后续Original HWM继承同一组合最近一期FINALIZED Settlement的Next HWM。
- 前序Settlement ID被持久化；Finalize时必须仍指向当前最近有效前序且HWM金额一致。
- 结算只能按时间向后锁定、按时间倒序作废；先作废上游或事后插入更早期间都会被服务端拒绝。
- Finalized覆盖期间内禁止新增该账户流水；若确需更正，必须先按倒序作废下游结算和Invoice。
- Period Rate分母为0时返回N/A并禁止Finalize。
- Closing Snapshot若提供，必须属于对应账户、日期等于Closing Date、具有Closing资格且金额完全相等。
- Beginning/Closing保存在账户明细，HWM保存在组合结算级；不得跨客户、平台或Fee Plan合并。

改变公式、舍入、日期边界或HWM继承逻辑属于高风险业务制度变更，必须有用户明确确认、回归样例和文档同步。

### 6.3 已确认目标与当前差距

- 6.2节中“同一组合继承HWM”和“组合结算级HWM”描述的是0.2.3当前代码，不再是用户目标。
- 目标是每个Sub Account独立拥有Original/Next HWM链、独立应用完整公式和20%费率，最后只汇总各账户已经计算完成的Service Fee。
- 账户A盈利和账户B亏损不得相互抵销后再决定收费；任何迁移必须用至少一个“一个账户盈利、另一个账户亏损”的反例测试锁定该规则。
- 目标Closing Snapshot为必填，不是“若提供才校验”；目标Beginning也必须有上一期Closing或明确期初Snapshot来源。
- 在Schema、API、迁移、UI和测试完成前，不得宣称上述目标已经实现。

## 7. OCR与Luna交叉核验

### 7.1 本地OCR流水线

`backend/app/services/statement_parser.py`负责：

1. 识别JPG/PNG/PDF真实格式。
2. PDF优先读取原生文字层；扫描PDF逐页渲染，最多20页图像OCR。
3. 长截图按重叠区域分段，减少窄列和超长表格遗漏。
4. 按版式关键词分类文档。
5. 提取客户、账户、计划、日期、余额、累计参考字段和基金持仓。
6. 生成字段置信度、警告、解析器名称与版本。

累计净供款和累计投资盈亏是lifetime参考，绝不能映射为本季度Contribution、Withdrawal或Gain/Loss。

### 7.2 Luna集成边界

`backend/app/services/codex_app_server.py`通过本地 `stdio` 使用Codex App Server：

- 不读取或保存OpenAI API Key。
- 使用应用专用 `FINANCIAL_CODEX_HOME`，不能指向用户桌面Codex的 `~/.codex`。
- 子进程环境主动清除外部 `CODEX_HOME`，并检查配置中没有插件、Hook、MCP或指令来源。
- 发送图片前检查ChatGPT认证模式、额度与精确模型可用性。
- 模型固定 `gpt-5.6-luna`，不接受前端覆盖，不升级到Terra/Sol，不调用第二模型。
- 每个导入记录只消费一次识别；并发点击通过进程内锁和幂等检查合并。
- 超时、额度、认证、协议、Schema、错误模型回执或静默重路由全部失败关闭，保留OCR并转人工。

### 7.3 比对和入账边界

OCR与Luna对标准化字段及基金名称匹配：

- `AGREED`：不存在冲突、缺失、不确定或不支持类型。
- `INCOMPLETE`：有单侧值、关键字段缺失、不确定字段或不支持文档类型。
- `CONFLICT`：双方标准化值不一致。

无论状态如何，`requires_financial_confirmation`始终为true。Luna接口只允许写StatementImport辅助字段和AuditEvent，不能创建或修改BalanceSnapshot、Transaction、Settlement、Invoice或Payment。确认时若存在冲突/不完整，财务必须显式勾选已逐项核对。

### 7.4 当前样本基线

2026-08-26的5份授权样本中：OCR文档分类5/5，Luna文档分类5/5；3份余额页四个关键字段OCR为12/12、Luna为10/12；两份非余额凭证均正确分流。完整条件、逐字段结果和改进建议见 `docs/客户账单OCR_Luna识别评估_20260826.md`。

真实样本测试会向OpenAI发送图片，必须获得用户对该文件的明确同意，且不得作为普通自动化测试自动运行。

## 10. 数据目录、迁移与备份

### 10.1 数据根结构

```text
<FINANCIAL_DATA_ROOT>/
  database/financial_system.sqlite3
  statement_imports/
  attachments/
  output/excel/
  output/pdf/
```

### 10.2 数据库启动迁移

- 正常启动运行Alembic到 `head`。
- `e91f7c6a2b40`为Settlement增加冻结Company/FC及`previous_settlement_id`，为现有数据回填当前归属和最近前序，并建立流水期间/HWM顺序的数据库Trigger兜底。
- 对早期没有 `alembic_version` 的MVP数据库，先创建缺失表，再按AI列和Settlement链字段判断迁移起点，不能把缺列旧库直接标记为head。
- 该兼容路径用于保留旧数据，不代表可以跳过新增迁移文件。
- 任何模型变更必须新增Alembic revision；禁止只修改ORM后依赖 `create_all` 修生产库。

### 10.3 备份与恢复

- 备份通过SQLite Backup API取得一致数据库副本，不直接复制运行中的数据库文件。
- ZIP包含数据库、`attachments`、`statement_imports`、`output`和 `manifest.json`。
- Manifest记录每个文件的SHA-256。
- 恢复先检查ZIP路径穿越和逐文件哈希，再写入 `pending_restore.json`。
- 真正替换在下一次应用启动、数据库初始化前执行。

恢复会替换业务数据目录中的数据库和归档文件，属于高风险操作；开发者不得在没有用户明确授权与可验证备份时执行。

## 15. GitHub协作与文档同步

**强制规则：对于项目每一次修改都要同步修改项目说明书。** 这里的“每一次修改”包括源码、测试、数据库迁移、API、UI、配置、依赖、构建、发布、脚本、协作规则和其他项目文件；不得等到交接时才批量补文档。

**业务背景同样必须实时交接。** 用户在对话中确认或修正的角色定义、业务原因、术语、计算/汇总边界、凭证要求、状态、例外、非目标和开发优先级，即使尚未修改代码，也必须在同一次任务中写入本文和CHANGELOG。对话记录、Agent记忆和历史工作报告都不能替代GitHub内的完整交接资料。

若目标规则尚未实现，必须同时记录“确认目标”和“当前实现差距”。新工程师或新Agent在重新询问用户前，必须先检索本文和专题文档；获得新答案后立即写回，防止跨会话背景损失。

### 15.1 每次任务的最小流程

```text
读AGENTS/项目说明书/CHANGELOG
  → 核对已确认业务背景与当前实现差距
  → 读相关代码和测试
  → 明确最小变更
  → 修改代码和测试
  → 同步项目说明书和CHANGELOG
  → 运行验证
  → 检查git diff
  → 提交并推送
```

任何项目文件发生修改时，必须在同一提交更新本文件；行为、业务规则、API、数据库、UI、OCR/Luna、依赖、构建、发布、安全边界或交付状态发生变化时，还必须更新 `docs/CHANGELOG.md`。用户确认新的项目背景或业务决定时，即使没有代码变更，也适用同一规则。

```powershell
python scripts/check-project-docs.py --base <基准提交SHA>
```

检查脚本会对除同步文档本身以外的项目改动强制要求本文件；行为代码、迁移、前端、构建或依赖变化还强制要求CHANGELOG。Pull Request模板用于人工复核同一规则。直接修改本文件本身即视为已同步；纯文字拼写修正可以不制造额外业务变更记录，但不得借“文档修正”掩盖行为变化。

### 15.2 禁止提交

- `data/`、`output/`、SQLite及WAL/SHM文件。
- 客户账单、微信图片、业务附件、OCR/Luna原始输出。
- `.env`、`auth.json`、`.codex`、Luna登录目录、密钥和令牌。
- `.venv`、`node_modules`、构建缓存、release、ZIP、EXE、DLL、PYD。
- 本地Tesseract/Codex二进制和机器专属配置。

## 16. 故障定位速查

| 现象 | 首查位置 | 处理原则 |
|---|---|---|
| EXE启动失败 | `%LOCALAPPDATA%/FinancialFeeSystem/launcher-error.log` | 先读错误；不要重复覆盖运行目录 |
| 提示8000占用 | 检查是否已有FinancialFeeSystem实例 | 先用页面安全退出；不要杀其他Codex进程 |
| 页面仍是旧UI | `/api/health`版本、实际启动路径、浏览器缓存/静态资源 | 确认启动的是唯一正式目录 |
| OCR不可用 | `TESSERACT_CMD`、语言包、`tools/Tesseract-OCR` | 保留上传和人工复核，不伪造OCR结果 |
| Luna显示未登录 | `GET /api/ai-assistant/status`、独立登录目录 | 只登录本系统专用环境 |
| Luna模型/额度不可用 | 状态接口的model/quota/auth结果 | 转人工，不换模型、不自动重试 |
| 导入不能确认 | 文档类型、关键字段、重复、账户匹配、AI冲突确认框 | 以服务端错误为准逐项修正 |
| Settlement不能Finalize | 分母、账户明细、Closing资格、状态 | 不绕过校验直接改数据库 |
| 提示存在前序变化或后续Settlement | `previous_settlement_id`、期间顺序、下游状态 | 重新Calculate或按时间倒序先作废下游 |
| Invoice不能建立/Issue | Settlement状态、Service Fee、Client资料、已有有效Invoice | 修复上游资料和状态 |
| PDF缺失 | Invoice归档路径和数据备份 | 从备份恢复；不要静默重生成覆盖已签发文件 |
| 恢复失败 | ZIP格式、Manifest、SHA-256、路径穿越检查 | 不手工绕过校验 |
| 数据库结构异常 | `alembic current/history`、迁移文件、旧库列 | 先备份并复现，禁止直接改生产库 |

## 17. 已知缺口与建议优先级

### P0：财务完整性

1. 当前Settlement/HWM按`Client + Platform + Fee Plan`组合计算；用户目标是每个Sub Account独立计算并维护HWM，账户间盈亏不得抵销。
2. 当前一条Settlement只能生成一张Invoice；目标是一张客户季度Invoice汇总多个独立Sub Account收费明细，并允许同一20%计划跨Platform合并出单。
3. Settlement API允许不传`closing_snapshot_id`并手填Closing；目标要求Closing必须关联符合资格的Balance Snapshot。
4. Beginning尚未关联`beginning_snapshot_id`；目标要求自动继承上一季度Closing或关联明确期初Snapshot。
5. Contribution、Withdrawal、Beginning、Closing和Payment凭证仍未成为相应正式状态的硬前置；业务标准已经确认，不再属于待确认事项。
6. Payment仍支持多笔/部分付款和四种派生状态；目标只保留未付款/已付款，并补齐公司承担小额差额、错误Invoice更正、退款和凭证审计流程。

### P1：报表与审计

1. FC统计仍包含Invoice已收/未收；目标只显示当前管理客户数、本季度收费客户数和Service Fee，不包含任何Payment指标。
2. AuditEvent前端不可查询，且并非所有普通资料修改都有完整事件。
3. Excel模板版本和导出契约尚无自动版本管理。
4. 进程若在预留Invoice编号后被强制终止，可能留下内部`ISSUING`状态；目前缺少启动时自动恢复界面，需要从审计和文件状态人工处置。

### P2：产品完整度

1. 多数基础资料、流水、快照和附件缺少完整更正/删除/冲正流程。
2. Company Logo字段存在，但缺少上传和配置界面。
3. 任意版式OCR、历史批量导入和浏览器E2E尚未实现。

用户已确认下一阶段继续把单机版做稳并投入实际使用；P0上述业务口径已经确认，但具体实施批次仍需在改代码前形成迁移、测试和验收计划。Defer及服务器/多用户不在近期范围。

## 18. 不可随意推翻的工程决策

- SQLite和本地文件：符合当前单机隐私与低部署成本；服务器化必须另做架构评审。
- Sub Account独立结算/HWM：每个账户先独立计算完整HWM与Service Fee，账户间不得抵销；跨Platform合并只发生在客户Invoice展示与总额阶段。
- Beginning/Closing和HWM均需保持Sub Account级来源及连续链；Closing必须来自合格Snapshot，Beginning必须继承上期Closing或明确期初Snapshot。
- 首次HWM人工输入：系统缺少安全推断依据。
- OCR + Luna双通道、人工最终确认：效率不能覆盖财务责任。
- ChatGPT管理登录而非普通API：满足用户不新增API费用的要求，但受订阅与模型可用性影响。
- 单模型失败转人工：保证成本、可审计性和结果稳定。
- Issue时编号且Void不复用：保证账单审计链。
- Settlement冻结Company/FC与前序ID：历史收费归属和HWM链不随主数据变化。
- 生成型下载使用POST：生成文件和ExportRecord属于写操作，必须经过本地写请求保护。
- Service Fee为0不生成付款Invoice：避免无应付款账单。
- 独立目录构建后再提升：避免端口占用、旧包运行和覆盖损坏。

## 19. Definition of Done

一项开发任务只有同时满足以下条件才算完成：

- 用户目标和业务口径已明确，未擅自扩展范围。
- 代码变化最小且遵循现有分层，没有绕过后端财务保护。
- 新增或修改行为有对应自动化测试。
- 数据库变化有Alembic迁移和旧库兼容验证。
- 金额、日期、状态、重复与失败路径均经过验证。
- 涉及真实图片/Luna时已取得云端上传同意，并单独报告真实验收范围。
- 对于项目每一次修改都要同步修改项目说明书；行为或交付状态变化还必须同步 `docs/CHANGELOG.md`。
- 用户新确认的业务背景和规则已在同一任务写入GitHub交接资料，并明确区分目标与当前实现差距。
- 后端测试、前端构建及风险相关的EXE/API/UI/导出验收已执行并报告结果。
- `git diff`中没有客户资料、凭据、二进制、构建输出或无关修改。
- 交付说明包含：改了什么、如何验证、是否触碰业务数据、遗留问题和Git提交状态。
